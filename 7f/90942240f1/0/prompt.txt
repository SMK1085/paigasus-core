## Verdict: APPROVE WITH CHANGES

The architecture is sound: a global `metrics`-facade lib mirroring `paigasus-logging`, bounded-cardinality labels, correct instrumentation sites, sensible scoping to the M0 surface, and a drift-test intent to keep ops artifacts honest. The substrate claims (relay `TickReport`, denial `dropped`, authz cache-hit branch, gateway/IAM router shapes, "gateway has no TraceLayer", "IAM has TraceLayer+TimeoutLayer") all check out against the code. But three MAJOR items are functionality/correctness bugs that would ship a non-working alert and an unbounded-cardinality vector, and must be resolved in the spec before coding: the outbox `parked` gauge semantics, the hand-waved tonic gRPC metrics layer, and the same-port unauthenticated `/metrics` under the gateway's non-internal deployment mode.

## Findings

### BLOCKER
None.

### MAJOR

- **Outbox `parked` gauge is modelled from a per-tick delta, so its alert essentially never fires** — §5.2 maps `iam_outbox_relay_parked` (gauge) from `TickReport.parked`, but that field is *"how many hit `max_attempts` and were parked THIS tick"* (`relay.rs:46-47`, incremented at `relay.rs:136`), and already-parked rows are excluded from future batches (`parked = false` filter, `relay.rs:107`). So the value is 0 on every tick that parks nothing new, even with thousands of parked rows accumulated. | Why it matters: `IamOutboxEventsParked: iam_outbox_relay_parked &gt; 0` (§7.2) would flap to 1 for a single scrape then reset to 0 — a growing parked backlog is invisible. | Suggested fix: make it a **counter** `iam_outbox_relay_parked_total` (sum of per-tick newly-parked) and alert on `increase(...[15m]) &gt; 0`; OR make it a true gauge backed by a `SELECT count(*) WHERE parked = true` (a new query the relay doesn't do today — call that out).

- **`oldest_unpublished_age_seconds` freezes when the relay stalls, and there is no relay-liveness alert** — the gauge is only refreshed per tick from `TickReport.oldest_unpublished_age_secs` (`relay.rs:116`), which is `None` on an empty batch and never updates if the relay task wedges while the process stays alive. | Why it matters: a stalled-but-alive relay is the exact failure the outbox observability exists to catch, yet `IamOutboxBacklogAgeHigh` reads a frozen gauge and `TargetDown (up==0)` won't fire (the process is up). | Suggested fix: add an alert on `rate(iam_outbox_relay_ticks_total[10m]) == 0` (relay not ticking), specify `None` → gauge 0, and note the gauge is only as fresh as `poll_interval_secs`.

- **The tonic gRPC metrics layer is hand-waved and hides two real problems** — §5.2 lists `iam_grpc_requests_total{service,method,grpc_status}` "via tonic metrics layer (`grpc/mod.rs`)", but (a) `grpc_status` is a **trailer** (`grpc-status`), sent after the response body, so a plain `map_response` tower layer over `Server::builder().layer(...)` (`grpc/mod.rs:56-67`) sees only the HTTP 200 head — capturing gRPC status requires wrapping the response body to observe terminal trailers (what tower-http's gRPC classifier does), and (b) `service`/`method` derived from `:path` are **unbounded** — a scanning client hitting `/foo/bar` mints arbitrary label values (tonic has no MatchedPath equivalent). | Why it matters: without trailer inspection there is no gRPC error signal at all (and IAM's primary surface from the gateway is gRPC); unbounded method labels are a cardinality-blowup/DoS vector that violates the spec's own §4.2 rule. | Suggested fix: either descope to rate/duration-only from a validated known-RPC set (collapse unknown paths to `&lt;unknown&gt;`), or specify tower-http gRPC classification / a body-wrapping layer for `grpc_status`; name the concrete mechanism, don't say "a tonic metrics layer."

- **No alert covers IAM gRPC errors** — §7.2's `IamHighErrorRate` is defined as "5xx ratio &gt; 5%", but gRPC responses are HTTP 200 + `grpc-status`; there is no 5xx on the gRPC path. The gateway's introspect/authorize calls are all gRPC. | Why it matters: IAM's hottest surface (machine-to-machine gRPC) has no error alert; only the gateway-side `GatewayIamDependencyUnavailable` partially compensates. | Suggested fix: add an `IamGrpcHighErrorRate` alert on the ratio of non-OK `grpc_status` (depends on the fix above), and clarify that `IamHighErrorRate` is HTTP-only.

- **`init` returning a `PrometheusHandle` on repeated calls is a foot-gun** — §4.1/§4.3 say `init` uses `install_recorder()` and "treats an already-installed recorder as a no-op ... Returns the render handle." But `install_recorder()` consumes the recorder built alongside the handle *before* install; on the second call the install fails and the freshly-built handle is **not wired to the global recorder**, so `render()` on it returns empty. | Why it matters: any process that calls `init` twice (the spec's own "second init is a no-op" unit test; or an integration test that builds the app twice) gets a disconnected handle whose `/metrics` is blank → false test failures and a silently-wrong endpoint. | Suggested fix: cache the first handle in a `OnceLock&lt;PrometheusHandle&gt;` and return a clone on subsequent calls; state that test isolation relies on nextest's process-per-test (cumulative process-global counters otherwise leak across tests under `cargo test`).

- **Same-port unauthenticated `/metrics` leaks telemetry under the gateway's non-internal deployment mode** — D4/§6.3 justify unauth `/metrics` by "M0 internal-only posture", but the referenced gateway-M0 D6 posture is "internal-only **OR** behind a hard spend cap." In the spend-capped-but-public mode, `/metrics` is merged onto the same listener as `/v1/chat/completions` (§6.1) and is reachable, unauthenticated, by any caller that can reach the proxy. | Why it matters: request volumes, error rates, upstream/IAM latencies are recon-grade information disclosure to an external attacker, and path-based firewalling on a shared port is L7-only (much harder than a port ACL). | Suggested fix: either bind `/metrics` to a separate internal bind-address, or explicitly narrow the RUNBOOK/D4 to state the spend-cap-only (non-internal) mode is **incompatible** with same-port unauth `/metrics` and requires network isolation regardless.

- **The G6 drift test reinvents PromQL parsing and will false-fail on histograms; the dep isn't budgeted** — §9 proposes parsing Grafana JSON + rule YAML to extract metric names and match `observability::names`. Robustly extracting *metric selectors* (not function names like `rate`/`sum`/`histogram_quantile`, label keys, template vars `$job`/`$__rate_interval`, nested `panels`/`templating`) needs a real PromQL parser (e.g. `promql-parser`) — a **third new dep** the §10 CI budget (`metrics` + `metrics-exporter-prometheus` only) doesn't account for — or a brittle regex. Critically, a registered histogram family `foo_seconds` is referenced in dashboards as `foo_seconds_bucket`/`_count`, which are **not** in `names`, so the test false-fails on every latency panel unless suffix-normalization is specified (it isn't). | Why it matters: a maintenance-burden test that reds CI on legitimate edits. | Suggested fix: prefer the standard tooling — `promtool check rules` / `promtool check config` (validates YAML + PromQL syntax cheaply, and `promtool test rules` can unit-test alerts) — and if a name-drift check is still wanted, use a real parser and strip `_bucket`/`_sum`/`_count`/`_total` before matching. Add promtool to the proto-pinned CLI toolchain (per the repo's cargo-deny/machete pattern).

### MINOR

- **"The `tracing::warn!` is retained for log visibility" contradicts removing the 60s ticker** — D5/§5.2 remove the throttled ticker (`main.rs:121-151`) whose whole purpose was to *rate-limit* the drop warning via `last_dropped` tracking, but claim the warn is retained. A warn at the drop site (`denial_audit.rs:73-75`) fires **per drop**, i.e. log spam during exactly the denial burst that causes overflow — the regression the ticker avoided. | Suggested fix: drop the warn entirely (the counter + `IamDenialAuditDrops` alert covers visibility), or state explicitly it moves to a throttled emit; don't claim "retained."

- **Removing the ticker may orphan `AppState::denial_buffer()` and trip `warnings = "deny"`** — the counter promotion bumps at the drop site, so `state.denial_buffer()` (used only at `main.rs:128` + tests) can become dead code, failing the workspace `warnings = "deny"` (`Cargo.toml:144`). | Suggested fix: note that the accessor must be removed or otherwise consumed.

- **Both service crates need a direct `metrics` dep, not just `paigasus-observability`** — instrumentation sites (`counter!` in `cedar_authorizer.rs`, `denial_audit.rs`, `relay.rs`, gateway `auth.rs:57,84`) live in the service crates and call the `metrics` macros directly. §10 only adds `paigasus-observability` as a `dependsOn`. | Suggested fix: state that `metrics` is a direct dep of both services (or that observability re-exports the macros), and account for it in machete.

- **Gateway IAM-call metrics are sourced in the auth middleware, not `chat`** — §5.3 says `gateway_iam_calls_total` is instrumented "in `chat`/`auth` around `introspect_api_key` + `is_authorized_self`", but the chat handler never calls IAM; both calls are in `auth.rs:57,84` (`require_iam_auth`). | Suggested fix: correct the source-site reference to the auth middleware only.

- **Streaming latency histograms measure time-to-headers, not full stream duration (unspecified)** — for SSE responses, `chat_completion` returns the head immediately and the body streams lazily after the handler returns (`chat.rs:86-95`), so both `gateway_upstream_request_duration_seconds` and the HTTP duration histogram capture TTFB, and the upstream metric won't see mid-stream terminal SSE errors. | Suggested fix: state the measurement boundary explicitly (TTFB) and that mid-stream failures are not counted as upstream errors.

- **`cache` label conflates a genuine miss with a Redis-outage bypass** — on a generations-read failure the authz call bypasses the cache entirely (`cedar_authorizer.rs:129-137`), which would record as `cache="miss"`, muddying cache-effectiveness. | Suggested fix: add a `bypass` value or note the conflation.

- **In-txn `PgAuditLog::record` counter can overcount vs. durably-committed rows** — instrumenting `record` (the in-txn twin, `pg_audit_log.rs` module doc) bumps `iam_audit_records_total{result="ok"}` even if the enclosing UoW later rolls back (row never becomes visible). | Suggested fix: acknowledge the counter measures insert-attempts-that-didn't-error, not committed rows.

- **IAM's existing `TraceLayer` will log every `/metrics` scrape** — `/metrics` merges into `router()` which `serve_http` wraps with `TraceLayer` + `TimeoutLayer` (`mod.rs:699-700`); §5.1 excludes `/metrics` from the RED layer but not from TraceLayer, so every ~15s scrape emits a request-span log. | Suggested fix: filter `/metrics` (and health) from the trace layer, or note the accepted noise.

- **`host.docker.internal` on Linux needs `extra_hosts` in the compose file, not a `docker run` flag** — §14 cites `--add-host=host.docker.internal:host-gateway`, but compose uses `extra_hosts: ["host.docker.internal:host-gateway"]`. For zero-click cross-platform, bake it into `docker-compose.yml`. | Suggested fix: specify `extra_hosts` in the compose and pin the Prometheus/Grafana image versions for reproducibility.

- **`iam_outbox_relay_drained_total` counts row-attempts (incl. retries/failures), not published events** — `TickReport.drained` = rows processed this tick including failures and re-attempts (`relay.rs:44-45`), so the "drain rate" SLO is muddy. | Suggested fix: also expose a `published_total` (drained − failures) or rename to reflect "processed."

### QUESTIONS

- Does `metrics-exporter-prometheus` with `default-features = false` avoid pulling `hyper`/`hyper-util` (http-listener) and any duplicate-hyper that could aggravate the known CI-disk-exhaustion issue with the cedar-bloated tree? Verify the resolved tree before merge.
- Under nextest (process-per-test) the global-recorder-once constraint is fine, but do any IAM/gateway integration tests build the app more than once in a single process? If so the `init` handle fix above is required, not optional.
- What does the `service` parameter to `init(service)` actually do, given §4.1 deliberately bakes in no per-metric `service` label? If it's only a startup log line, say so.
- Slice B is almost entirely static artifacts (dashboards, rules, compose, RUNBOOK). Beyond the name-drift check, is there any CI gate that the alert rules parse and the dashboards are valid? Without `promtool`, "operator can see the dashboards" (G4) is only manually verifiable — is that acceptable to close the epic?

## What's good

- **The global-facade choice and its justification are correct and well-argued** — instrumentation sites span HTTP handlers, a tonic server, a background relay, and the authz cache; threading a `Registry` through every `AppState` would be far worse. Mirroring `paigasus-logging`'s accepted global-state tradeoff is the right call and keeps `AppState::new` signatures untouched.
- **The cardinality discipline (§4.2/D8) is genuinely load-bearing and mostly right** — closed-enum labels, `model`/PRN/path exclusion preserving the gateway privacy bar (`chat.rs:106-109`), and MatchedPath templating with an explicit `&lt;unmatched&gt;` collapse for HTTP 404s. Keep this rigor; just extend it to the gRPC path (see MAJOR).
- **Scoping gateway metrics strictly to the M0 auth+proxy surface (D3) and deferring provider/cost/cache metrics to gateway-M5** correctly avoids instrumenting surfaces that don't exist, and the coordination note with the gateway-M0 doc is precise.
