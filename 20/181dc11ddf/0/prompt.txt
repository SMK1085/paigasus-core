## Findings

### BLOCKER

- **Three integration-test assertions break and are unmentioned** — The spec's "Tests that must change" section lists only unit tests inside `src/`. It misses `rs/crates/services/paigasus-iam/tests/http_memberships.rs:150` and `:156` (`assert_eq!(err["error"]["code"], "invalid-prn")` for the `provide exactly one of principal|node` case) and `rs/crates/services/paigasus-iam/tests/http_audit.rs:109` (`invalid-prn` for `GET /v1/audit?cursor=not-a-uuid`). All three are migration sites. | Why it matters: these are `assert_eq!` on a runtime JSON value, so they are a **compile-time pass and a test-time red** — and every one of them is behind `support::start_migrated_postgres()`, so a Docker-less run reports them as skipped/quiet while CI reds. The spec's own claim that "leaving one behind is a compile-time pass and a silent behavioural miss" applies here and it did exactly that. `ci/error-registry/check.py`'s `SCAN_GLOB = "**/src/**/*.rs"` (line 77) does not scan `tests/`, so no gate flags them either. | Suggested fix: add a "Tests that must change" row for `tests/http_memberships.rs:144-156` and `tests/http_audit.rs:98-110`; state explicitly that `tests/http_authz.rs:222` is **not** affected (its `"principal_prn": "not-a-prn"` goes through the genuine PRN parser `http/authz.rs:72`, not `:145`), so a reader does not "fix" it by mistake.

- **`conflicting-fields` is structurally unreachable on gRPC; the two sites are not the same failure** — `grpc/tenancy.rs:611-615` matches a proto3 `oneof` (`list_memberships_request::Filter`). A `oneof` can never carry two values on the wire, so `None` there means **neither field set**, i.e. `missing-required-field`, never "conflicting". `http/memberships.rs:93-97` uses `match (q.principal, q.node)` with a `_ =&gt;` catch-all that folds **both** `(None, None)` and `(Some, Some)` into one arm. | Why it matters: (a) the spec assigns `conflicting-fields` to a gRPC site where the condition is impossible, so the reason is a lie; (b) HTTP now returns one reason for two distinct client mistakes, which is precisely the catch-all this ticket exists to remove, at smaller scale; (c) the two transports emit different reasons for "neither field set", and the spec's own parity table exempts this row so nothing catches it. `tests/http_memberships.rs:148-156` exercises both cases and would now assert the same code for both. | Suggested fix: split the HTTP arm — `(None, None) =&gt; MissingRequiredField("principal|node")`, `(Some(_), Some(_)) =&gt; ConflictingFields("principal|node")` — and reclassify `grpc/tenancy.rs:614` as `MissingRequiredField("principal_prn|node_prn")`. Counts become `missing-required-field` = 5 sites, `conflicting-fields` = 1 (HTTP-only). Then state plainly that `conflicting-fields` has no gRPC emitter and why.

- **AC-3 is not met: the migration *creates* cross-transport reason divergence on 9 of 18 sites** — The spec asserts AC-3 needs "HTTP and gRPC agree on the reason for the same logical failure", then exempts the rows where they now *disagree*:
  - `missing-required-field` (3 sites, all HTTP): the gRPC twins pass the field straight through and yield `invalid-prn` — `grpc/authz.rs:236` (`roles.list(&amp;actor, &amp;req.principal_prn)`), `grpc/service_accounts.rs:142` (`parse_node_prn(&amp;req.owner_prn)`), `grpc/service_accounts.rs:177` (`parse_node_prn(&amp;req.scope_prn)`). Same logical failure, two different reasons.
  - `invalid-uuid` (4 sites, all gRPC): the HTTP twins use axum's `Path&lt;Uuid&gt;` extractor (`http/memberships.rs:82`, `http/api_keys.rs`), which is **not** wrapped in `EnvelopeJson` and produces axum's default plain-text rejection — not even the `{"error":{code,message}}` envelope, let alone `invalid-uuid`. The parity table has no `invalid-uuid` row at all.
  - `invalid-timestamp` on `expires_at`: gRPC `grpc/service_accounts.rs:184` yields `invalid-timestamp`; HTTP's `IssueApiKeyBody.expires_at: Option&lt;DateTime&lt;Utc&gt;&gt;` (`http/dto.rs:464`) fails in serde and yields axum's `JsonRejection` path. No parity row.
  | Why it matters: SMA-508 AC2 requires the SDK to branch on `(domain, reason)` alone. An SDK author writing one branch per logical failure will get different reasons depending on transport for half the new vocabulary — a worse contract than today's uniform (if wrong) `invalid-prn`. | Suggested fix: for each of the six reasons, add an explicit "gRPC emitter / HTTP emitter / divergence accepted?" row. Where divergence is accepted, say so in the spec and in the proto comment. Where it is not, migrate the twin (e.g. give the three gRPC sites an explicit empty-string check emitting `MissingRequiredField`, and wrap `Path&lt;Uuid&gt;` in a custom extractor emitting `InvalidUuid`) or explicitly defer with a follow-up issue.

### MAJOR

- **The parity guard tests the cases that cannot drift and skips the cases that already have** — Both transports derive `reason` from the *same* function: `http/error.rs:35` uses `self.0.code()` and `grpc/convert.rs:125` uses `e.code()`. So for a given `TenancyError` variant the reason is **identical by construction**; parity can only break where the two transports construct *different variants*. The five table rows all construct the same variant on both sides, so the guard's five rows are near-tautological; the rows where different variants are constructed are exactly the ones excluded. | Why it matters: the guard reads as satisfying AC-3 while proving almost nothing new beyond the existing AC-4 membership test. | Suggested fix: keep the table but drive `to_filter` / `into_request` rather than the raw `parse_*` helpers (that at least proves the helper is still *wired*), and add a table row per excluded site asserting the two transports' variants explicitly, so the divergence is either fixed or visibly recorded as a red-or-documented fact rather than an omission.

- **The field name is unreachable by any spec-compliant consumer** — D2 puts the field name only into `Display`, which lands in the gRPC `Status` message and the HTTP `"message"`. SMA-508 AC2 (quoted by the spec as its forcing function) forbids branching on message text. The HTTP envelope is positively pinned to exactly `{code, message}` by `http/error.rs:106-110` (`the_error_object_key_set_is_unchanged`), so HTTP has no structural channel for it at all. | Why it matters: a console that wants to highlight *which* form field failed can do so on neither transport without the message parsing the design forbids — so the whole benefit D2 claims over option 1 accrues only to a human reading a log. | Suggested fix: put the field name in `ErrorInfo.metadata["field"]` for gRPC — the mechanism already exists and is already used for `capability` (`grpc/convert.rs:96-104`) and is documented as an open map in `error.proto:36-42` — and state explicitly that HTTP deliberately carries it in prose only, or extend the HTTP envelope (which requires changing `the_error_object_key_set_is_unchanged`). Either way, decide it in the spec.

- **No "Acceptance criteria → design" table and no "Compatibility" section** — The sibling spec `docs/superpowers/specs/2026-08-23-sma-583-grpc-audit-timestamp-bound-design.md:228-243` carries both. SMA-586's spec cites AC-2, AC-3, AC-4 and AC-5 in passing, never states any of them, and never mentions AC-1 at all. | Why it matters: a reviewer cannot check coverage, and AC-1 is silently unaddressed. More importantly, this changes the wire `reason` for existing, mounted failure modes — a breaking change for any consumer, which `error.proto:21-25` explicitly says `buf breaking` cannot see and which the registry's append-only guarantee does **not** cover. The spec's only compatibility statement is "`:breaking` — clean. Adding enum values is additive", which is true and beside the point. | Suggested fix: add both sections. The Compatibility section must state that no released client branches on `invalid-prn` for these 18 sites (verify: the only cross-service consumer is `paigasus-gateway/src/adapters/http/auth.rs:228`, which matches `identity-not-provisioned` only — the spec's "gateway needs no change" claim is correct), and that this is a deliberate one-shot break taken before SMA-508 ships.

- **Widening the helpers to `pub(crate)` is not sufficient — the modules are private too** — `rs/crates/services/paigasus-iam/src/adapters/http/mod.rs:19` and `:24` declare `mod audit;` and `mod dead_letters;` with no visibility. ### MINOR

### QUESTIONS

- `http/authz.rs:145` and `http/service_accounts.rs:71` fire `missing-required-field` only when the query param is fully **absent**. `?principal_prn=` (present, empty) yields `Some("")`, which falls through to a PRN parse and still returns `invalid-prn`. `MembershipQuery` (`http/dto.rs:181-186`) likewise has no `opt_non_empty` filter, unlike every other query struct in the module. Is "present but empty" intended to be a different reason from "absent", and if not, does the migration add the `opt_non_empty` normalisation?
- D2 rejects option 1 partly because "today's server-side context is lost from logs too". `status_to_grpc` (`grpc/convert.rs:118-121`) and `ApiError::into_response` (`http/error.rs:28-33`) log **only** on `ErrorClass::Internal`, so the `InvalidPrn` payload is currently logged nowhere for these Validation errors. Which logging is this referring to?
- ADR-0019 quotes example spellings and `paigasus-proto/src/error.rs:316-321` pins them (`the_adr_examples_are_spelled_as_documented`). Does the Notion ADR-0019 vocabulary section need a six-row update, and is that in scope?
- The spec's Scope says "18 production sentinel sites across **four** kinds" while the design defines six. Which is the intended count for the plan's task breakdown?
- Was a materially simpler alternative considered: emit one new reason `invalid-field` plus a `metadata["field"]` key, rather than six reasons? It would satisfy SMA-508 AC2's "branch on reason" only weakly, so probably rightly rejected — but the spec never names it, and the D1 rationale for six would be stronger for having done so.
