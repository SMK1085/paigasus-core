## Issues

**Minor 1 — `connect_succeeds_for_default_tls_system_trust` couples to the host trust store** (`client.rs:392-403`). I traced the eager path: `build_channel` → `endpoint.tls_config()` (tonic `channel/endpoint.rs:377-382`) eagerly calls `into_tls_connector`, and for `with_native_roots` the connector build (`channel/service/tls.rs:87-94`) does `if certs.is_empty() { return Err(NativeCertsNotFound) }`. So `IamClient::connect(&amp;default_cfg).await` returns `Err` in any env with no system trust store (minimal/distroless/scratch runner without `ca-certificates`), failing this `assert …is_ok()`. It is green in this repo's CI (which ships ca-certificates), and the brief did mandate a system-trust connect test, so this is not a blocker — but it is a real latent trap, not fully avoidable while asserting `is_ok()` on the native-roots path. Mitigation for a follow-up: test the system-trust branch against a bundled test-CA PEM (`ca_cert_path`), or `tls-webpki-roots` compiled-in roots, so the assertion doesn't depend on ambient host state. (Production behavior — fail-fast at boot when system-trust TLS is configured but no trust store exists — is correct and should stay.)

**Minor 2 — stale G3 config doc after G4's pinning decision** (`config.rs:49-50`). The `ca_cert_path` field doc still reads "to trust, in addition to (G4 decides: instead of, or alongside) the system trust store." G4 has now decided "instead of" (pins). Not in G4's diff and documented correctly at the use site, but a one-line update there would prevent an operator from assuming custom CA augments system roots. Low priority.
