## Verdict: READY-WITH-FIXES

This is a strong, well-researched design that accurately reflects the M0 codebase (transactional aggregate creation, PRN reuse, partial-unique-index NULL trap, composite-FK denormalization, correct CI/affected-graph impact). But it has two blocking specification gaps — the domain-error-code mapping contradicts the very DB-only strategy it adopts, and the archive/restore semantics (own vs effective status) that are the heart of D1 are ambiguous — plus several MAJOR concurrency/testability/wiring gaps that will cause divergent implementations. Fix the BLOCKERs and MAJORs and it is safe to build.

## Findings

### BLOCKER

- **Unique-violation → specific domain code is unimplementable as specified** (§3.4, §5.2) — §3.4 removes `find_by_slug` and leans entirely on the DB unique index ("surfaced as `Conflict` on insert/rename"), yet §5.2 demands *distinct* codes `slug-conflict` vs `duplicate-membership` (and there is a third unmentioned case: the `prn` UNIQUE column). The M0 `map_err` this spec claims to reuse collapses *every* `SqlErr::UniqueConstraintViolation(_)` into one generic `Conflict("unique constraint violated")` precisely to avoid surfacing the PII-bearing PG DETAIL. There is no specified way to get from "some unique constraint fired" to the correct kebab code without inspecting the constraint identity. | Why it matters: the §5.2 transport table (409 `AlreadyExists` with a specific code) cannot be honored; two engineers will build different mappings, and a `prn` collision has no code at all (falls to generic 409 or 500). | Suggested fix: give every unique index a deterministic name in the migration (e.g. `uq_org_slug`, `uq_team_org_slug`, `uq_membership_principal_org`, …), and have the adapter map `DbErr` → domain code by matching the *constraint name* (names are not PII), with a documented fallback code for the astronomically-unlikely `prn` collision. State this mechanism in §3.4/§5.2.

- **Archive/restore semantics are ambiguous on own-vs-effective status** (§2 D1, §5.1 rules 1–3) — the spec never states whether `archive`/`restore`/idempotency operate on a node's *own* status or its *effective* status, and the rules interact incoherently. "Archive is idempotent (no-op on archived)" — own or effective? Rule 2 makes an *effectively*-archived node read-only "except restore," but restore only clears the *own* flag; so `archive(team)` when `team` is effectively-archived-via-ancestor (own = Active) is either (a) rejected as a write on a read-only node, leaving no way to set the team's own flag, or (b) allowed, contradicting rule 2. Likewise `restore` on an own-Active node is undefined (no-op or error). | Why it matters: this is the central mechanic of D1; the ambiguity yields materially different behavior (e.g. whether restoring an org silently un-archives children that an operator tried to archive during the outage) and different test expectations. | Suggested fix: state explicitly that `archive` sets/`restore` clears the node's **own** status only; idempotency is on own status; `archive`/`rename`/child-create are rejected when the node is **effectively** archived, but `restore` is always permitted and acts on own status (no-op if own is already Active). Add a truth table for the org-archived × team-own-archived matrix.

### MAJOR

- **Archived-parent guard and org-membership invariant are TOCTOU-racy; isolation level unspecified; child-create guard is not in the write transaction** (§3.4, §5.1 rules 1 &amp; 4) — `MembershipRepository.attach` is specified as "checks + inserts in one transaction," but atomicity ≠ isolation: under Postgres default READ COMMITTED, a concurrent `archive(org)` (an UPDATE on a different row) does not conflict with the membership INSERT, so a membership can be attached to a node that became effectively-archived mid-transaction. Worse, the child-create guard (rule 1) is done in the application service via a separate `repo.find(parent)` read *before* `repo.create(child)` — two transactions — so it is racy *and* inconsistent with the in-transaction membership guard. | Why it matters: the archived-parent and org-membership invariants are advisory, not enforced, and the spec claims they are enforced. | Suggested fix: state the isolation level; enforce the parent-not-archived and org-membership checks inside the same transaction as the insert, taking a row lock on the ancestor(s) (`SELECT … FOR SHARE`) or using `SERIALIZABLE` with retry; or explicitly document the guards as best-effort and accept eventual repair.

- **Derived-status logic lives only in SQL — leaky/anemic core and a fake-vs-real divergence trap** (§3.4, §5.1, §7) — "effective status computed in SQL by joining the ancestor chain" puts the core business rule (`effective = own ∨ any-ancestor-archived`) in the persistence adapter, not the pure domain. The §7 service unit tests use in-memory fakes that must *reimplement* that rule; if the fake and the SQL diverge, unit tests pass while production is wrong, and the rule is untestable in the pure crate this repo's DDD conventions favor. | Why it matters: the invariant guards (parent-archived) depend on effective status, so a divergence is a correctness bug that the test pyramid cannot catch below integration level. | Suggested fix: put a pure `effective_status(own, ancestors) -&gt; NodeStatus` in `paigasus-iam-core`, have both the fakes and the app-layer guards call it, and either (a) compute it in core from repo-returned ancestor statuses, or (b) keep the SQL computation for read performance but add an integration parity test asserting SQL output equals the core function.

- **List endpoints have no defined ordering, archived-filter, or bound** (§3.4 `list*`, §6.1, §6.2) — offset pagination with no `ORDER BY` is nondeterministic in Postgres: pages will skip/duplicate rows. It is also unstated whether lists include effectively-archived nodes (or filter them, or flag them), and `limit` has no default/max/validation (a caller can request `limit=10_000_000`). | Why it matters: broken pagination is a concrete data-correctness bug; the archived-filter ambiguity means two engineers build different list semantics; unbounded limit is a trivial DoS on an unauthenticated admin API. | Suggested fix: specify a stable sort key (e.g. `ORDER BY created_at, id`), state whether lists include archived nodes (recommend include + return `effective_status`), and define default/max `limit` and validation for negative/zero `limit`/`offset`.

- **Principal and node existence checks for `attach` are unspecified and land on the wrong error path** (§5.1 rule 9) — `principal_prn` "must resolve to an existing principal" and `node_prn` to an existing node, but the mechanism is undefined. The M0 `PrincipalRepository` exposes only `create_user`/`find_user` (no existence probe), and if `attach` relies on the FK to catch a missing principal/node, a foreign-key violation is *not* a `UniqueConstraintViolation`, so M0's `map_err` routes it to `Backend` → **500**, not the `not-found` → 404/`NotFound` the taxonomy promises. | Why it matters: attaching to a nonexistent principal/node returns 500 instead of a clean 404, and there is no port to pre-check the principal. | Suggested fix: add an existence port (e.g. `PrincipalRepository::exists(&amp;PrincipalId)`), pre-check inside the attach transaction, and/or map FK-violation `DbErr` to `not-found`; state which.

- **Node resolution must not trust the client-supplied PRN's org slot** (§5.1 rules 4 &amp; 9, §6.1) — a team/project `node_prn` encodes the org UUID in its org slot, and the org-membership invariant needs "the node's org." If the implementation reads the org from `node_prn.org()` (it is right there), a caller can forge a PRN with a valid team `resource_id` but a *different* org slot and have the invariant checked against the wrong org. | Why it matters: it silently breaks the D3 invariant now and is a latent authz-bypass foundation for M2. | Suggested fix: resolve the node by `resource_id` against the DB, derive org from the *persisted* row, and reject the request if `node_prn.canonical() != stored_prn`.

- **No API path to create a Principal in M1, yet AC-1 requires attaching one** (§6.2, §9) — `CreateUser` "stays unwired (M2)" and there is no other principal-creation endpoint, so a running M1 service has zero principals and every `AttachMembership` fails; the AC ("attach a principal via Membership") is only reachable by inserting principals through the repo directly in integration tests. | Why it matters: the milestone ships a membership feature that cannot be exercised end-to-end through its own API. | Suggested fix: either wire a minimal principal-create endpoint for M1, or explicitly state that principals are seeded via test-only repo inserts and that `AttachMembership` is non-functional in a real deployment until M2 — and confirm the AC is satisfiable under that constraint.

### MINOR

- **Node PRN reconstruction for `list_by_principal`/`list_by_node` needs joins that aren't specified** (§3.4, §6.1) — a team/project membership row stores only `team_id`/`project_id` (exactly-one-nonnull CHECK), but returning `node_prn` requires the node's org UUID, i.e. a join to `team`/`project`. Call this out so the read model isn't under-built.
- **Membership `modified_at` contradicts the AuditMetadata contract** (§6.1) — memberships set "created_at only," but `AuditMetadata` documents "modified_at equals created_at on first write." Leaving `modified_at` null deviates from the shared contract; set `modified_at = created_at` or amend the contract note.
- **DELETE membership idempotency/status code undefined** (§6.2) — unclear whether deleting a nonexistent membership returns 404 (`not-found`) or 204 (idempotent). Pick one.
- **Create-org response shape (with default team) is unspecified** (§5, §6.1, §6.2) — the service "returns both," but no `CreateOrganizationResponse { organization, default_team }` (proto) or HTTP body shape is given.
- **`ListMemberships` "exactly one filter" isn't structurally enforced** (§6.1) — two optional strings invite both-set/neither-set bugs; use a proto `oneof` and define the both/neither HTTP behavior (recommend `InvalidArgument`).
- **Proto parent-PRN field names for Team/Project are unspecified** (§6.1) — "parent PRN(s)" is ambiguous; name them (`Team.org_prn`, `Project.team_prn` + `Project.org_prn`).
- **Name length unit ambiguous** (§3.1) — "≤ 256 chars" (Unicode scalar values vs bytes vs graphemes) affects validation; specify.
- **Raw-SQL migration reversibility &amp; PG-specificity not addressed** (§4) — `num_nonnulls`, partial indexes, and CHECKs are Postgres-specific and need explicit `down()` handling; M0's `down()` precedent should be matched.
- **"default" slug is reserved-by-provisioning per org** (§5.1 rule 7) — a user creating a team with `slug="default"` hits a conflict they didn't cause; document it.
- **`updated_at` advancement on archive/restore/rename is implied but not stated** (§3.2, §5.1) — state it explicitly.

### QUESTIONS

- What transaction isolation level do the guarded operations use? (Drives the MAJOR concurrency finding.)
- Is `restore` on an own-Active node a no-op or an error?
- How are principals created in M1 for the membership tests and for real use — seed via repo, or wire `CreateUser`?
- What are the default and maximum `limit` values for list endpoints?
- Is it an accepted deployment constraint that these unauthenticated admin endpoints are never internet-exposed before M2 (no authn, no rate limiting, no body-size cap beyond axum defaults)? Worth stating explicitly.
- gRPC uses PRNs everywhere while HTTP uses UUID paths + PRN bodies — is the surface asymmetry intentional, and is uuid↔prn translation on the caller acceptable?
