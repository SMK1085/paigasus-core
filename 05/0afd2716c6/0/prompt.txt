  ## 4. WebFetch of https://claude.com/resources/articles/building-always-on-agents
  
  The fetch worked. The tool returned a summary, not the raw page. Quotes below are what it returned.
  
  - **Inbox**
    - Route every event source (webhooks, schedules, background jobs, user messages) into a durable inbox, not straight into the agent. Reason: direct calls start competing runs and lose events on a crash.
    - Use a DB table with status per event and dedup by source identifiers.
    - Keep the handler fast. Acknowledge quickly and defer injection screening to the run.
    - The inbox is the source of truth. A replacement worker re-reads pending events, so a crashed run can be retried.
    - Start with one inbox per user. Split only for parallelism.
  - **Single worker per inbox**: only one active worker per inbox. A mid-run event has three options: queue for the next run, fold into the current run, or interrupt and restart.
  - **Batching**: merge pending events into one run. Several user messages produce one reply.
  - **Timers vs inbox**
    - Keep timers in a separate store. The inbox holds only events ready to work.
    - Follow-ups are self-set deadlines. Schedules are recurring and track recurrence.
    - "Timers never start runs directly." A scheduler polls at a fixed interval. For each due timer it marks follow-ups done, advances schedules and adds an inbox event.
  - **Session resume vs fresh**
    - Events that continue earlier work (a user reply) resume the session. Others start a new session.
    - A new session loads baseline overhead (system prompt, tools, memory) plus the trigger. A resumed session brings back the full transcript.
    - Keep the baseline lean and use prompt caching.
    - When a session grows too long, compact or start new. Both lose detail, so "anything that needs to persist should be saved to memory" first.
  - **Mid-run events and deferral**: while a deferred tool call waits, the run ends and the session is saved mid-call. The worker handles other events meanwhile.
  - **Memory**
    - Keep it in a durable store that outlives workers.
    - Rule: "memory should only hold what the agent can't look up again". Store a pointer for data held elsewhere.
    - Four kinds: user instructions (loaded every run), user notes (index first, files on demand), past messages (what the user was already told), task progress (per-task file).
  - **Dreaming**: periodically review past sessions to curate memory. Replace outdated entries and surface cross-run patterns.
  - **Permissions / defer**
    - Each tool call can proceed, block or wait for approval.
    - Auto mode uses classifiers to block dangerous actions. "User review, however, is still necessary for the most important decisions."
    - A deferred call shows the request to the user. The answer returns as an inbox event that resumes the saved session in a new run.
  - **Credentials proxy**: keep credentials outside the agent environment. The agent sends requests without them. A proxy adds the real credentials before forwarding.
  - **Outbox: notify vs silent**
    - A run ends one of three ways: send a message, stay silent, or issue a deferred request.
    - Most agents can use a direct "send" tool. Add a formal outbox (table plus dispatcher) only to pace messages or recover from delivery errors.
    - Tune volume with evals. "start quiet and then earn more of the user's attention over time".

  **Implications for the ADR (my inference)**
  - "End the run cleanly on needs-approval, resume later" is not supported by the SDK.
  - A workaround that stays inside current APIs: use a `PermissionPolicy` or `ApprovalHandler` that records the pending call to your outbox and returns `Deny`. The model then sees the denial as a tool result and the run ends normally. On approval, call `Runner::run` with a new user message carrying the approval answer, against the same session.
  - This needs the session reloaded by your own id string (Postgres or SQLite `open(pool, session_id)`).
  - It is unverified whether the model re-issues the call cleanly after a Deny.
  - For mid-run interrupt, only `CancellationToken` exists.
