## 4. `next.config.ts` (verbatim) and `createNextConfig`

```ts
import { fileURLToPath } from 'node:url';
import { createNextConfig } from '@paigasus/next-config';

export default createNextConfig({
  zone: 'iam',
  basePath: '/iam',
  outputFileTracingRoot: fileURLToPath(new URL('../..', import.meta.url)),
  extend: { experimental: { authInterrupts: true } },
});
```

`createNextConfig` (`ts/packages/paigasus-next-config/src/index.ts`) accepts `{ zone, basePath, assetPrefix?, outputFileTracingRoot, extend? }`. It:
- rejects `extend.env` (env is factory-owned; deployment values must go through `@paigasus/next-config/runtime` instead)
- rejects a `zone` with leading/trailing whitespace or empty
- canonicalizes `basePath` via `canonicalBasePath`
- merges `SOURCE_ONLY_PACKAGES` (`@paigasus/app-shell`, `@paigasus/auth`, `@paigasus/discovery`, `@paigasus/kernel`, `@paigasus/next-config`, `@paigasus/proto`, `@paigasus/sdk`, `@paigasus/ui`) into `transpilePackages`
- unconditionally forces `output: 'standalone'` (cannot be overridden by `extend`)
- writes `env: { PAIGASUS_COMPILED_ZONE, PAIGASUS_COMPILED_BASE_PATH }` (build-time-baked image identity — the only two "NEXT env" values allowed, distinct from `NEXT_PUBLIC_`)

A second app would call this the same way with a different `zone`/`basePath` (e.g. `zone: 'gateway', basePath: '/gateway'` per the `.env.local.example` comment referencing SMA-512).

## 5. Auth wiring

- **Route handler**: `app/auth/[...auth]/route.ts` — one catch-all handler mounting `createAuthRouteHandler` from `@paigasus/auth/server`, keyed by a `WeakMap&lt;AuthRuntime, handler&gt;` so the handler is built once per runtime; `GET`/`POST` both delegate to `handle()`.
- **`proxy.ts`** (repo root of the app) — Next 16's name for middleware. Imports only `@paigasus/auth/middleware` (never `/server` or the sdk — enforced by `paigasus-next-config` boundary tests). Two jobs: (1) cookie-presence-only auth gate via `createAuthMiddleware({ publicPaths: [...authRoutePaths(), '/', '/healthz'], loginPath: '/auth/login' })`; (2) mints a per-request correlation id header and a request-path header. `config.matcher` excludes `_next/static`, `_next/image`, `favicon.ico`.
- **`lib/auth.ts`** — the composition root: `authRuntime()` calls `getAuthRuntime(getRuntimeConfig(), { logger, resolver: createIntrospectPrincipalResolver(...) })`; also defines `SESSION_COOKIE_NAME = '__Host-pgs_sid'` (not exported by `@paigasus/auth` itself).
- **`lib/iam.ts`** — per-request React `cache()`-wrapped accessors: `currentSession` (redirects to login), `iamClients`, `optionalSession`, `iamClientsForAction` (server-action-safe, returns a `relogin` failure instead of redirecting), `sessionToken`.
- **`lib/correlation.ts` / `lib/correlation-header.ts`** — reads/writes `CORRELATION_HEADER` and `REQUEST_PATH_HEADER` via `next/headers`; `FORBIDDEN_VIEW_CORRELATION` constant records whether the 403 view can read the header.
- **`lib/prn-tenancy.ts`** — hand-written PRN parser for IAM's three tenancy shapes (`organization`/`team`/`project`), held to parity with the Rust kernel by `tests/unit/prn-tenancy.test.ts` replaying `rs/crates/libs/paigasus-kernel-parity/vectors/**`. Recorded ADR-0005 exception (kernel napi/wasm bindings don't work in a Next build).
- **`lib/config.ts`** — the app's one `defineRuntimeConfig` call, composing `authEnvShape` + `discoveryEnvShape` + `PAIGASUS_IAM_GRPC_URL` (a zod transform validating an absolute http(s) URL with no credentials/query/fragment) and a refined `PAIGASUS_SERVICES` requiring an `iam` entry.
- Other `lib/` files: `authorize.ts` (`mayI`), `discovery.ts`, `errors.ts`, `form.ts`, `iam-clients.ts`, `logger.ts`, `nav.ts`, `paging.ts`, `principal*.ts`, `scopes.ts`, `tenancy-path.ts`.

## 11. `repo:next-public-free` and `repo:next-env-drift` gates

- **`repo:next-public-free`** (root `moon.yml:903-943`, script `ci/next-public/run.sh`): bans `NEXT_PUBLIC_` anywhere under `ts/` (packages included, not just apps — a source-only package inlines the same way when transpiled) and requires every app's Next config to go through the `@paigasus/next-config` factory. Discovery is **generic**: `APP_CONFIG_GLOB='ts/apps/*/next.config.[tjmc][sj]*'` (`ci/next-public/run.sh:184`), so a second app is automatically covered, no registry edit needed. Runs `--self-test` and `--negative-control` before the real run (all three required by `set -euo pipefail`, pinned by `SELF_SCHEDULED_GATES`). `inputs` use `ts/**/*` minus negated `.next`/fixture-`.next` globs (also generic `ts/apps/*/...`).
- **`repo:next-env-drift`** (root `moon.yml:130-155`, script `ci/next-env/run.sh`): asserts the committed `next-env.d.ts` matches what `next typegen` emits. **Hard-coded to one app**: `APP='ts/apps/iam-console'` (`ci/next-env/run.sh:26`); the moon task's `deps: ['iam-console-ts:build']` and `inputs` (`ts/apps/iam-console/{next-env.d.ts,next.config.ts,tsconfig.json,app/**/*}`, plus `ts/pnpm-lock.yaml`) are also iam-console-only. A second app would need either its own copy of this gate/script (parameterized by app dir) or an extension of this one to loop over both apps — currently it silently does not check a second app's `next-env.d.ts` at all.

## 12. Dockerfile / standalone image build

- **No Dockerfile exists for iam-console** (or for any Next.js app) anywhere in the repo. `find -iname "Dockerfile*"` only finds `rs/Dockerfile` (the Rust services image, used for `paigasus-iam` and `paigasus-gateway` binaries — unrelated to Next/console apps).
- `.github/workflows/images.yml` only triggers on `rs/Dockerfile` changes (line 28) and builds/smokes the two Rust service images via `ci/images/run.sh`; it has no Next/console image target.
- `ci/images/run.sh` (`build`/`smoke`/`all` subcommands) is entirely Rust-service-specific: `crate_for()` maps only `iam`→`paigasus-iam` and `gateway`→`paigasus-gateway`; `assert_pins()` checks `rs/Dockerfile`'s Rust toolchain/Ubuntu/chisel pins; `smoke()` runs `paigasus-gateway:dev` and `paigasus-iam:dev` containers with Postgres. # What a new Next.js "gateway console" zone would talk to

## 1. `rs/crates/services/paigasus-gateway` — HTTP surface

**Router:** `rs/crates/services/paigasus-gateway/src/adapters/http/mod.rs`

Three route groups, all merged into one `axum::Router` (mod.rs:82–113):

| Route | Method | Auth | Notes |
|---|---|---|---|
| `/healthz` | GET | none | liveness only (mod.rs:102, 115–117) |
| `/readyz` | GET | none | probes IAM reachability via a sentinel introspect (mod.rs:103, 143–155) |
| `/v1/chat/completions` | POST | `require_iam_auth` (auth + D9 self-query authz) + `DefaultBodyLimit` | mod.rs:93; handler `chat::chat_completions` |
| `/v1/service-info` | GET | `require_authenticated` (auth only, **no** authz) | mod.rs:98–99; handler `service_info::get_service_info` |

- **OpenAI-compatible surface:** yes — `POST /v1/chat/completions`, modeled on the OpenAI chat-completions request/response shape (`rs/crates/services/paigasus-gateway/src/adapters/http/dto.rs:22-34`, `ChatCompletionRequest{model, stream, messages, ..extra}` with `#[serde(flatten)]` for lossless passthrough of any other OpenAI field). Errors render through an "OpenAI error envelope" (`adapters/http/error.rs`, referenced throughout `chat.rs`).
- **Streaming (SSE):** yes. `chat.rs:121-144` proxies OpenAI's SSE stream verbatim as `Content-Type: text/event-stream`, unbuffered, and if the upstream fails mid-stream it emits one terminal `data: {"error":{...,"code":"upstream-error"}}\n\n` frame (`chat.rs:63`, `terminal_sse_error_stream` at `chat.rs:206-220`) rather than changing the already-committed HTTP status. Streaming is gated by config: `stream_enabled` (config.rs:34) → `Capabilities.chat_stream` (service_info.rs:19-28); if `stream:true` is requested while disabled, the gateway returns `400`/`param: "stream"` (`chat.rs:104-106`).
- **Ports/transports:** **one HTTP port only, no gRPC server** (main.rs:6-7: "one HTTP port, no gRPC server, no DB"). Config key `http_addr` (default `0.0.0.0:8088`, `config.rs:187`). The gateway is itself a gRPC **client** to IAM (`iam.grpc_addr`, default `https://127.0.0.1:9090`, `config.rs:75`) and dials it lazily on start (main.rs:79). Metrics can share the HTTP port or bind separately via `metrics.addr` (`config.rs:127-144`).
- **Authentication:** Bearer token only, via the standard `Authorization: Bearer &lt;token&gt;` header (`adapters/http/auth.rs:303-314`, `fn bearer`). No cookies, no query params (auth.rs:54). The `/v1/chat/completions` path additionally requires D9 self-query authorization against IAM (`is_authorized_self`, auth.rs:94-124) for the `InvokeModel` action; `/v1/service-info` requires only that the bearer authenticates (`require_authenticated`, doc at auth.rs:126-153), specifically to let a caller who can't invoke models still discover capabilities. Egress hygiene: the caller's bearer is never forwarded to OpenAI (chat.rs:15-18).
- **Router file:** `rs/crates/services/paigasus-gateway/src/adapters/http/mod.rs`
- **Handler files:** `adapters/http/chat.rs` (chat proxy), `adapters/http/service_info.rs` (discovery), `adapters/http/auth.rs` (middleware), `adapters/http/dto.rs` (request DTO), `adapters/http/error.rs` (OpenAI-envelope error rendering), `adapters/http/bytes.rs` (body-limit extractor).

**Chat/streaming client already exists** (`src/chat.ts`) — this directly answers the "SMA-625 mentions sdk error mapping and chat" question:
- `createChatClient(options, auth)` at `chat.ts:197` builds a client for **`POST {baseUrl}/v1/chat/completions`** — doc comment explicitly: "The gateway's `POST /v1/chat/completions` — the one hand-written HTTP surface" (chat.ts:187).
- It is **`fetch`-based, not gRPC** — "This client uses `fetch` and builds no `Transport`" (chat.ts:194-195). `options.fetch` is an injectable per-call seam (chat.ts:145).
- Sends `Authorization: Bearer &lt;token&gt;` (chat.ts:241), refuses an empty/whitespace bearer at call time (chat.ts:201-203).
- Branches on `response.headers.get('content-type')` for `text/event-stream` vs JSON (chat.ts:268-276) and returns the **raw, unread `ReadableStream&lt;Uint8Array&gt;`** for streaming (`kind: 'stream'`, chat.ts:275) so cancellation propagates to the upstream connection.
- Bounds only the wait for response **headers** (`DEFAULT_HEADER_TIMEOUT_MS = 10_000`, chat.ts:132), never the stream body itself, matching the gateway's own TTFB semantics.
- `createTerminalFrameParser(committedStatus, ids)` (chat.ts:30) is a standalone, caller-driven SSE scanner for the gateway's one terminal error frame (`code: "upstream-error"`, matching `chat.rs:63`), deliberately not auto-wired so the SDK never buffers the passthrough stream itself.
- Errors go through the same `mapError`/`PaigasusError` machinery as the gRPC IAM clients, so a gateway-console would reuse `./errors` unchanged.

## 6. `ts/packages/paigasus-auth` — multi-zone story

- `PAIGASUS_ZONE`/`PAIGASUS_ZONES` are **not** declared by `paigasus-auth`'s own `authEnvShape` — they are explicitly forbidden there because they're owned by `@paigasus/next-config`'s `defineRuntimeConfig` (`src/config.ts:6-9`, "throws if an extra shape declares `PAIGASUS_ZONE` or `PAIGASUS_ZONES`"). They arrive into `createAuthRuntime` via the composed config type `ComposedConfig = AuthEnv &amp; { PAIGASUS_ZONE: string; PAIGASUS_ZONES: Record&lt;string,string&gt; }` (`src/runtime.ts:51-54`).
- **The reject-memory-with-multiple-zones rule**, `src/runtime.ts:105-113`:
  ```ts
  if (cfg.PAIGASUS_SESSION_STORE === 'redis') {
    requireRedisUrl(cfg); // Invariant 1
  } else if (Object.keys(cfg.PAIGASUS_ZONES).length &gt; 1) {
    throw new AuthConfigError('PAIGASUS_SESSION_STORE cannot be "memory" when PAIGASUS_ZONES declares more than one zone');
  }
  ```
  Rationale in the comment directly above it: "the memory store... is single-process... under multi-zone the zones share nothing — a user who logs in on zone A is anonymous on zone B... A startup error beats that silent wrong answer."
- README (`ts/packages/paigasus-auth/README.md:84-94`) restates this: each zone in a multi-zone deployment is a **separate Next process**; under `memory` a user signed in on zone A is anonymous on zone B; `createAuthRuntime` refuses to start with `memory` + &gt;1 zone; use `redis`.
- **Cookie**: `src/http/cookies.ts:21` — `export const SESSION_COOKIE = '__Host-pgs_sid';`. Attributes from `serializeCookie` (`cookies.rs`… actually `cookies.ts:46-52`): `HttpOnly`, `Secure`, `SameSite=Lax`, **`Path=/`**, no `Domain` (forced by the `__Host-` prefix). README: "all zones share **one cookie on one origin**" (README.md:132-133) and design comment in `runtime.ts:75`: `/** All zones share one cookie on one origin (design doc § 6.7) — never per-zone, never configurable. */ cookieDomainless: true`.
- **What makes a second zone able to log a user in independently:** with `PAIGASUS_SESSION_STORE=redis`, all zones/processes on one origin share **one Redis-backed session store** (`keyPrefix: ''`, no per-zone prefix — `runtime.ts:140-148`, comment: "All zones share ONE store (design doc § 6.7) — no per-zone key prefix to configure") and **one `__Host-pgs_sid` cookie scoped `Path=/`** across the whole origin. So a gateway-console zone doesn't need its own login flow at all for an *existing* session — it reads the same cookie, looks it up in the same Redis store, and sees the user already authenticated. It *does* still need its own `/auth/login`, `/auth/callback`, `/auth/logout`, `/auth/logout/callback` routes mounted under its own base path (`README.md:105-125`, `createAuthRoutes`), each zone deriving its own OIDC redirect URIs from `PAIGASUS_PUBLIC_ORIGIN + &lt;this zone's basePath&gt; + /auth/callback` (`runtime.ts:129-130`) — so a user landing directly on the gateway zone with no session can still independently kick off its own OIDC round trip, which then writes the one shared cookie/session record any zone can subsequently read.
- Per-zone runtime singleton is cached under a **zone-keyed** `Symbol.for` slot (`runtime.ts:196-230`, `RUNTIME_KEY_PREFIX = 'paigasus.auth.runtime.v1'`, `runtimeKey(zone)`), specifically so two zone apps composed into one process (a documented future case, SMA-513) don't collide on one runtime.
