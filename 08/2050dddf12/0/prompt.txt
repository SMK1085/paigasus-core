## Strengths

- **The D9 self-query is structurally uncrossable, not just tested.** In `adapters/http/auth.rs:71-85` both the queried `principal_prn` and the bearer `key` come from the *same inbound request* (the introspect response + the inbound `Authorization`), and `adapters/iam/client.rs:124-134` builds the `IsAuthorized` request faithfully from those args with no principal substitution. There is no code path that lets a caller name a principal other than the one their own key resolves to. The unit test (`auth.rs:388-404`) records and asserts the exact 4-tuple.
- **The introspect-vs-authz `PermissionDenied` divergence is correct across the service boundary.** I traced it through IAM: `grpc/convert.rs::authn_status` maps `PrincipalInactive → PermissionDenied` and `InvalidToken → Unauthenticated`; the gateway's `introspect_error` (auth.rs:109-120) maps `PermissionDenied → 401` while `authz_error` (auth.rs:126-137) maps `PermissionDenied → 500`. Invariant #5 holds exactly, and both mappings are exhaustive.
- **Credential hygiene is enforced by the type, not by discipline.** The chat handler (`chat.rs:78`) hands the egress client only `body: Bytes` — it is *impossible* to forward a caller header because the client never receives them (`openai/client.rs:165-172` builds a fresh request with only `Authorization`/`Content-Type`/`Accept`). Proven at two levels (`openai_egress.rs:108`, `chat_proxy.rs:296`, incl. cookie + exact-match bearer). OpenAI key is `SecretString`, redacted in `Debug` and `#[serde(skip_serializing)]` (config.rs:99), locked by tests.
- **D11 cache path is proven no-DB-read.** `cache_hit_returns_scope_prn_without_a_db_read` (authenticate_api_key.rs:638) uses `PanicIfCalled*` repos, and both introspect mappers (`grpc/convert.rs:314`, `http/dto.rs:520`) extract `scope_prn` from the identical `Credential::ApiKey` match, so miss/hit/gRPC/HTTP are consistent by construction. `WireValidation` round-trips it through Redis JSON (cache.rs:359).
- **Streaming + cancel-on-drop is genuinely proven.** The handler returns the adapted stream directly (chat.rs:134-148, `unfold` owning the inner stream), and `client_abort_cancels_upstream_request` (chat_proxy.rs:373) drives a real socket + a `Drop`-guard mock to prove propagation with a bounded fail-not-hang. TLS is ring-only: `aws-lc` absent from `rs/Cargo.lock`, `ring` present; the Cargo.toml comments (lines 34-38, 52-57) document *why*.
- **`gateway_user` did not dilute anything (D10).** `GATEWAY_USER_ACTIONS = &amp;[InvokeModel]` (roles.rs:155); I read every `*_ADMIN_ACTIONS`/`*_MEMBER_ACTIONS` const — none contains `InvokeModel`. `is_write=true` (action.rs:190) flows into the derived `forbid-archived-writes`, and the archived-deny is table-tested for `gateway_user` (roles.rs:599).

### Minor

1. **Silent 500s on the auth path — observability gap (highest-weight Minor).** `error.rs:58` documents `GatewayError::Internal` as "*details are logged, not echoed*", but the auth middleware does **no** logging — the only request log is in the chat handler (`chat.rs:107`), which never runs on a middleware short-circuit. So an authz `PermissionDenied → 500` (a *broken D9 self-query* — precisely the thing you must be able to see in prod) or `MissingScope → 500` (a plumbing bug) produces **no log line at all**. `file: adapters/http/auth.rs:69,81` + `adapters/http/error.rs:58`. Fix: add a `tracing::error!`/`warn!` on the `MissingScope` and `authz PermissionDenied→Internal` arms (no token/scope values), or at minimum soften the doc comment. Non-blocking for internal M0, but I'd do the one-liner now.

2. **`ca_cert_path` doc contradicts behavior (security-adjacent).** `config.rs:49-50` says the custom CA is trusted "*in addition to … the system trust store*", but `iam/client.rs:191-197` **pins to that CA alone** (`with_native_roots` only on the `None` branch). An operator reading the config doc could wrongly assume public roots still validate. `file: config.rs:49-50`. Fix: one-line doc correction to "trust *only* this CA (replaces the system trust store)". Cheap; I'd fix before merge.

3. **`BadRequestBody` message imprecise.** Valid JSON missing a required `model`/`messages` field also yields "The request body is not valid JSON" (`error.rs:109`, `chat.rs:69`; the DTO fields aren't `#[serde(default)]`). Status 400 is correct; only the message is off for that sub-case. Acceptable as-is.

4. **Spec-shorthand vs implementation on "upstream 5xx".** The impl forwards an upstream **HTTP** 5xx *verbatim* (chat.rs:81-84, `ChatResponse::Full` with upstream status), reserving `502/504` for transport-level connect/timeout/build failures (`error.rs:73-80`). This is the *more faithful* proxy semantic and matches spec §5 ("return upstream status verbatim") and the 429-passthrough test — but it diverges from a literal reading of D12/§7 "upstream-5xx→502". Not a bug; worth a one-line spec note so the two spec statements don't read as contradictory. No e2e 502/504 row exists (unit-proven only) — optional follow-up.

5. **Auth runs before the 413 for authenticated callers.** `mod.rs:64-68` (documented at :63-65): a valid caller sending an oversized body incurs *two* IAM round-trips before the body-limit rejects it. Unauthenticated callers still 401 at the header stage before the body is read, so exposure is limited to valid callers. Acceptable for M0/non-prod (D6); a follow-up could pre-check `Content-Length`.

6. **Stale Cargo.toml comment.** `Cargo.toml:73` references `tests/health.rs`, which doesn't exist (tests are `chat_proxy.rs`/`openai_egress.rs`). Trivial.
