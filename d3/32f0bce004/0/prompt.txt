<result>## Verdict: NEEDS REWORK

The spec is unusually well-argued and its instincts (derive-plus-floor, containment-vs-strict-equality, stating limitations) match the repo's standards. But three of its four substantive decisions rest on an unexamined assumption — that keying a task on the *source* of a copied/installed artifact makes the task *observe* the change — and the repo has already measured that assumption false in both stacks. On top of that, §1's motivating example for A7 is factually wrong (an existing `run.sh` case already reds it), and A7's floor as specified cannot catch the vacuity §7's own test #3 claims it catches. These are design-level, not plan-level, and must be settled before code.

## Findings

### BLOCKER

- **§4 D3's input-keying half is vacuous by the same mechanism F1 condemns** — basedpyright reads `py/.venv/.../paigasus_py_bindings/__init__.pyi` (the maturin-installed copy), not `rs/crates/bindings/paigasus-py-bindings/paigasus_py_bindings.pyi`. `py/pyproject.toml`'s `tool.basedpyright.include` is `["packages/*/src/**", "packages/*/tests/**"]`, so the source stub is *never read by the task at all*. `py:typecheck`'s script is `uv run basedpyright …` (`.moon/tasks/python.yml:38`) — plain `uv run`, no `--reinstall-package`. This repo has already measured that plain `uv run` serves a cached maturin wheel and cannot observe a change in that crate's tree (`py/packages/paigasus-kernel/moon.yml:21-22`; `ci/affected-graph/run.sh:325-329`: "a kernel edit that made `--reinstall-package` fail 67 tests left plain `uv run pytest` reporting 124 passed"). uv's default rebuild trigger for a path dependency is a `pyproject.toml`/`setup.py` change, and the stub is neither. | Why it matters: the newly-scheduled `py:typecheck` run re-reads the *stale installed* stub and passes — scheduling without coverage, the exact shape §4 F1 uses to reject SMA-535's filed fix, reproduced one level down. The spec would ship an input that is a pure cache key over a file the task never opens. | Suggested fix: either (a) add `[tool.uv.cache-keys]` to `rs/crates/bindings/paigasus-py-bindings/pyproject.toml` listing `paigasus_py_bindings.pyi` (and the Rust sources) and *measure* that a `.pyi`-only edit rebuilds the wheel, or (b) add `uv sync --reinstall-package paigasus-py-bindings &amp;&amp;` to the typecheck script, or (c) drop the input entirely and state plainly that the drift gate is the whole of the coverage. Do not ship (a)/(b) unmeasured.

- **§5's ts input-keying is vacuous by the identical mechanism, already measured in-repo** — `tsc -p tsconfig.json --noEmit` resolves `@paigasus/node-bindings` through `node_modules`, and `ts/packages/paigasus-kernel/tsconfig.json` declares no `paths` mapping. The package is a pnpm `file:` dep (`ts/packages/paigasus-kernel/package.json:40-41`), and this repo's own comment records the measurement: "pnpm COPIES a `file:` dep into its store at install time and never re-copies a rebuilt binary, so loading via the package name would import a STALE store .node (verified)" (`ts/packages/paigasus-kernel/moon.yml:99-102`). The vitest tasks work around this with an explicit alias; `tsc` has no such alias. | Why it matters: keying a typecheck task on the crate-dir `index.d.ts` re-keys the cache but `tsc` still reads the store copy. §5 delivers zero coverage while reading as a fix — and since §5 also excludes the drift half (deferred to SMA-434), the entire ts half of this spec would land with no coverage at all. | Suggested fix: settle *what tsc actually reads* before designing the input. Options: a `paths` mapping in the kernel tsconfig pointing at the crate dir (mirroring the vitest alias), or `pnpm install --force`/`link:` instead of `file:`, or drop §5 and fold ts entirely into SMA-434. Measure with a hand-edit to `rs/crates/bindings/paigasus-node-bindings/index.d.ts` and a `moon run paigasus-kernel-ts:typecheck --force`.

- **§1's motivating example for A7 is false, and §7's negative controls inherit the error** — "Deleting `/rs/crates/libs/paigasus-kernel/src/**/*` from `paigasus-kernel-ts:build` leaves every gate green" is wrong. `ci/affected-graph/run.sh:343-344` (`run_task_case_ci "kernel-&gt;consumer-tasks"`, strict equality) explicitly lists `paigasus-kernel-ts:build`, `paigasus-kernel-ts:test` and `paigasus-kernel-py:test` in the expected set for a touch of `rs/crates/libs/paigasus-kernel/src/lib.rs`. Removing that glob makes the task un-affected and the case reports it as `missing`. The mechanism is also misdescribed: the ts parity replay is `vitest`, which runs in `:test`, not `:build`. | Why it matters: this is the entire stated justification for A7. If the reviewer takes it at face value the gate is approved on a defect that cannot occur; if they check it, the spec's credibility on every other "measured" claim drops. It also makes §7 tests 2 and 3 useless as A7 controls — both mutations red an *existing* run.sh case, so a green/red outcome proves nothing about A7. | Suggested fix: restate the motivation with a hole that is genuinely uncovered — e.g. deleting `/rs/crates/bindings/paigasus-wasm/src/**/*` from `paigasus-kernel-ts:test` (no `run.sh` case touches a wasm-binding source *and* asserts `kernel-ts:test`; the project-level `binding-oneway-wasm` stays green via `:build`'s wasm glob). Rewrite §7's per-row controls to use only mutations that no other assertion in the suite can see, and say so.

- **A7's floor as specified cannot catch A7's actual vacuity mode** — D4/D5 define `REQUIRED_WRAPPER_TASKS` as a set of *task names*, and D5 states "for A7 the floor **is** the task set". But A7's real vacuity mode is `rust_closure` degrading to empty (a moon rename, a `dependencies` key reshape, a `language` field change on the bindings crates): `want` becomes `{}`, containment `want ⊆ observed` is vacuously satisfied, and A7 prints PASS for all three tasks while asserting nothing. A task-name floor is silent on that. §7 test 3 ("Simulate an emptied derivation and confirm the `FLOOR:` rows fire") therefore describes a control the specified floor cannot pass. A6 does this correctly with `REQUIRED_CLOSURE_EDGES` (`ci/affected-graph/cargo_moon_parity.py:129-132`) — a per-consumer *edge* floor, plus a membership half at `:339-343`. | Why it matters: this is the repo's #1 recurring failure mode, and the spec cites it correctly one paragraph before getting it wrong. | Suggested fix: A7 needs **two** floors: the task set *and* a closure floor, e.g. `REQUIRED_WRAPPER_CLOSURE = {"paigasus-kernel-ts": {"paigasus-kernel-rs","paigasus-node-bindings-rs","paigasus-wasm-rs"}, "paigasus-kernel-py": {"paigasus-kernel-rs","paigasus-py-bindings-rs"}}`, with `FLOOR:`-prefixed rows and a self-test control that matches the prefix (A6's `A6-e` at `:801-810` is the pattern, including its warning that emptying `deps` also empties `want` and produces confusable rows).

### MAJOR

- **§6/D5 and §5 directly contradict each other about `paigasus-kernel-ts:typecheck`** — D5 excuses that task from A7 because it "legitimately observe[s] nothing, and should not". But `paigasus-kernel-ts:typecheck` is the inherited `tsc -p tsconfig.json --noEmit` (`.moon/tasks/typescript-project.yml:38-45`), it is *not* overridden by the project's `moon.yml`, `:typecheck` **is** in `ci.yml:214`'s `T` array, and `src/index.ts:2` imports `@paigasus/node-bindings` — so it is precisely the task §5 says must key on the committed glue. §9 Q4 then asks whether that task exists at all, after §5 already decided. | Why it matters: after §5 lands, D5's stated rationale is false and A7's floor is missing a task that now observes upstream crates — but if you add it to the floor, containment demands the kernel crate dir on a task where only the glue is the interface. The design has no answer. | Suggested fix: resolve §9 Q4 *in this spec*. State whether the glue input goes on `paigasus-kernel-ts:typecheck` or on `:build` (where `tsc --noEmit` already runs as the tail of the script, `ts/packages/paigasus-kernel/moon.yml:43`), and either add typecheck to `REQUIRED_WRAPPER_TASKS` with a documented containment exception or record why it stays out.

- **§5 does not establish that it closes any defect `:build` doesn't already close** — `paigasus-kernel-ts:build` regenerates the glue and then runs the *same* `tsc -p tsconfig.json --noEmit`, and already keys on all three Rust binding sources plus the kernel. `:typecheck` is a byte-identical command with a subset of the inputs. The only defect §5 uniquely closes is a hand-edit to committed glue with no Rust change — and SMA-434 covers that. | Why it matters: SMA-536 was folded into scope on a symmetry argument (§2), but the symmetry is cosmetic: py gets a drift gate, ts gets a duplicate of an existing check via an input that (per the BLOCKER above) probably doesn't work. That is scope for its own sake. | Suggested fix: name the concrete defect §5 closes and the mutation that demonstrates it, or drop SMA-536 from this spec and let SMA-434 own the ts side entirely.

- **D1 stops one file short of fixing the hole it identifies, twice** — `cargo fmt --check` formats *every* target in the package: `src/**`, `tests/**`, `benches/**` and `build.rs`. `fmt.inputs` is `['@group(sources)']` = `src/**/*` only (`.moon/tasks/rust.yml:83-85`). So the same "config/file edit invalidates no `fmt` task" hole exists for `@group(tests)` and `build.rs`, and for `/rs/rust-toolchain.toml` (which selects the rustfmt binary — the exact argument `.moon/tasks/rust.yml:63-67` makes for putting it on `lint`). A misformatted integration test can merge green today and red `main` on an unrelated later src edit. | Why it matters: the spec touches this exact line and leaves three-quarters of the hole open, which will read to the next engineer as a deliberate decision. | Suggested fix: `fmt.inputs: ['@group(sources)', '@group(tests)', '/rs/rustfmt.toml', '/rs/rust-toolchain.toml']` plus whatever mechanism D2 picks for `build.rs`; or state explicitly why tests/ and the toolchain pin are excluded.

- **D1's new input has no assertion guarding it, in a spec whose whole thesis is that unasserted inputs rot** — nothing checks `fmt`'s inputs. A4 (`check_lint_inputs`, `cargo_moon_parity.py:198-230`) asserts the three workspace files on every crate's `lint` for exactly this reason; the equivalent for `fmt` does not exist, and §7 item 6 proposes only "a new ad-hoc probe", which is not a durable assertion. D2 gets an assertion; D1 does not. | Why it matters: the spec's own cited lesson — SMA-524's "a MISSING case is how the bug survived" — applies identically. | Suggested fix: extend `check_lint_inputs` into a generic `check_task_inputs(projects, crates, task, required)` and call it for `lint` (3 files) and `fmt` (rustfmt.toml + rust-toolchain.toml), with a self-test row per task.

- **The `build.rs` assertion (D2) and the stub-drift gate (§4) are both unreachable as designed** — `repo:affected-smoke`'s `inputs` (`moon.yml:165-202`) contain no `build.rs` glob and no `rs/crates/**/src/**` glob. So: (a) adding a `build.rs` to an *existing* crate without touching its `Cargo.toml` does not schedule `repo:affected-smoke`, and D2's filesystem-derived assertion serves a cached PASS on exactly the PR it exists for; (b) if the stub-drift gate is folded into `cargo_moon_parity.py` (§9 Q2's cheaper option), a PR that adds a `#[pyfunction]` schedules nothing that runs it. `moon.yml:181-192` already documents this precise trap for the actionlint and release-parity pins: "the pin is real but unreachable: the PR that deletes those lines does not schedule this task." | Why it matters: this is the same class the spec's own §6 anti-vacuity reasoning is about, applied to scheduling rather than derivation. | Suggested fix: add `rs/crates/*/*/build.rs` to `repo:affected-smoke`'s `inputs`; if the drift gate is folded in, also add `rs/crates/bindings/paigasus-py-bindings/src/**/*` and `.../paigasus_py_bindings.pyi`. Both then acquire `repo:input-liveness` obligations. State this in the spec, not the plan.

- **A7 at crate-dir granularity will permanently certify a real existing hole as green** — neither wrapper declares `/rs/crates/libs/paigasus-kernel/Cargo.toml`. `ts/packages/paigasus-kernel/moon.yml` lists the kernel's `src/**/*` (:55, :131) but the kernel's `Cargo.toml` nowhere; `py/packages/paigasus-kernel/moon.yml:46-51` likewise. `repo:parity-corpus-drift` lists it explicitly for exactly this hazard ("a kernel Cargo.toml change (a future `[features]` toggle altering `sum`) must re-key the gate" — `moon.yml:214-217`). A6 demands *both* `src/**/*` and `Cargo.toml` per upstream (`cargo_moon_parity.py:357-360`); A7 as specified demands neither at file granularity. | Why it matters: §6's "measured" table reports the wrappers as correct because it looks at crate *directories*. L3 states the granularity limitation abstractly but does not disclose that a live under-declaration exists today and will be blessed. | Suggested fix: fix the wrappers first (add the kernel's `Cargo.toml` to all three tasks), then either tighten A7 to demand `src/**/*` + `Cargo.toml` per closure member (a containment check can be file-granular without becoming strict equality) or rewrite L3 to say which real inputs are currently missing and why that is accepted.

- **A name-level drift gate must compare three sets, not two, and the spec does not say how it derives the Rust name** — `rs/crates/bindings/paigasus-py-bindings/src/lib.rs` has 12 `#[pyfunction]` attributes *and* 12 separate `m.add_function(wrap_pyfunction!(…))` registrations (`:123-134`). A `#[pyfunction]` that is never registered does not exist at runtime, yet a two-set comparison (attrs vs stub defs) reports agreement. PyO3 also supports `#[pyo3(name = "…")]`, which renames the Python-visible symbol; D3 says "the stub's `def` names match the Rust `#[pyfunction]` set" without saying whether the Rust name is the fn ident or the PyO3 name. | Why it matters: two engineers will build different gates, and the more obvious one has a silent hole. | Suggested fix: assert `{pyfunction idents (PyO3-name-aware)} == {wrap_pyfunction! registrations} == {stub def names}`, and add a self-test row for each of the three pairwise mismatches (§7 test 5 currently names only two directions).

- **The R1 fallback is materially larger than one sentence suggests** — "route `build.rs` through a `fileGroups` entry the shared template already consumes" has no existing candidate group. `.moon/tasks/rust.yml` consumes `sources`, `tests`, `upstreams`; adding a new `@group(buildscript)` makes its absence a hard graph-load error (`project::unknown_file_group`) for *every* moon command in the repo, so all 13 crates must declare it, 12 of them empty. That is a bigger change than the "shared template" option D2 rejected, not a lightweight fallback. | Why it matters: the fallback is what the design falls back to if R1 goes the wrong way, so it needs to be as costed as the primary. | Suggested fix: name the actually-cheap fallback — declare `build.rs` inside the crate's existing `fileGroups.upstreams` (A6's `observed` filter at `cargo_moon_parity.py:399-401` excludes `own/`-prefixed entries, so it passes A6 untouched) — and verify that claim before relying on it.

- **§9 Q2 under-costs a new `repo:*` task by two registries** — the wiring cost is not just `T` + CLAUDE.md + input-liveness. Every gate added since SMA-572 is registered in **both** `SELF_SCHEDULED_GATES` (`ci/affected-graph/ci_targets.py:309-422`, whole-line pins of its `moon.yml` script lines including `set -euo pipefail`) **and** `SELF_TASK_EXPECTED_GLOBS` (`:184-248`) or a reasoned `SELF_TASK_GLOBS_EXEMPT` entry; `check_registry_pairing` (`:1079`) reds if a script-pinned gate has neither. §7 item 8 also says "all 27 targets", which is today's count (`ci.yml:214`) — i.e. it silently assumes the *folded-in* option that §9 Q2 leaves open. | Why it matters: the decision between "new task" and "folded in" changes both the PR size and the §7 test plan, and the spec presents contradictory assumptions in two sections. | Suggested fix: decide it in the spec; if a new task, enumerate `T`, the CLAUDE.md marker block, `SELF_SCHEDULED_GATES`, `SELF_TASK_EXPECTED_GLOBS`, `repo:input-liveness`, and bump §7's count to 28.

It would not be silent: A4 (`check_lint_inputs`) reds immediately for that crate's `lint`, and A6 reds for all three tasks (`paigasus-node-bindings-rs` has a non-empty `upstreams` group). | Suggested fix: keep the measurement (it is still the right first step) but correct the consequence — the existing gates catch replace-semantics loudly.

- **D4's "only the *root* language filter changes" is imprecise** — `rust_closure` (`cargo_moon_parity.py:279-305`) has no root language filter; the root filter lives in `check_upstream_inputs`'s `examined` set (`:331`). - **§7 item 6's `moon query tasks --affected` probe will not observe `fmt`** — `_assert_task_case_impl` filters to names `build`/`test`/`lint` (`ci/affected-graph/run.sh:94-97`), so if the probe is later promoted into a `run.sh` case it will report nothing. ### QUESTIONS

- If both BLOCKERs above hold (installed-artifact staleness in py and pnpm store staleness in ts), is anything left of SMA-535/536 beyond the drift gates? If not, should this spec be reduced to SMA-560 (A7) + SMA-537, with 535/536 re-scoped as "make the checker read the fresh artifact"?
- What is the intended answer to §9 Q3 (keying a typecheck task on a file another task regenerates)? `paigasus-kernel-ts:build` and `:typecheck` have no dependency edge and run concurrently under `moon ci`; `build` rewrites `index.d.ts` (it is *not* in the task's declared `outputs`, `ts/packages/paigasus-kernel/moon.yml:89-96`). Does typecheck's input hash get computed before or after? If nondeterministically either, the cache key is unstable — that is a design-level answer, not a plan-level one.
- §6's containment argument is sound *as an argument*, but does the "fruit salad" problem actually exist? Every non-crate input in both wrappers lives outside `rs/crates/` and is already filtered out by A6's `startswith("rs/crates/")` test. The only genuine extra is the `kernel-parity` vectors dir. Would a strict-equality A7 with one `ALLOW_OVER_APPROXIMATION`-style entry for `kernel-parity` be strictly stronger at the same cost — and if so, does L2 ("a wrapper may over-declare permanently") need to be accepted at all?
- Is `paigasus-kernel-py:build` deliberately excluded from A7 forever, or only until it does something (`uv build` currently packages only the pure-Python wrapper)? If the latter, what makes A7 notice the day it changes?
- §7 says the re-baseline "may turn out empty". My read of `ci/affected-graph/run.sh` agrees for all four proposed inputs (no case touches `rs/rustfmt.toml`, `build.rs`, the `.pyi`, or `index.d.ts`; `fmt`/`typecheck` are outside the task-case name filter). Do you want the plan to *assert* that emptiness (e.g. by adding cases that touch these files), so the four new inputs acquire behavioural coverage rather than only declarative coverage?
