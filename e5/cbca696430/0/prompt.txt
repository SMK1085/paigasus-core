## Verdict: APPROVE WITH CHANGES

The design is fundamentally sound: hexagonal layout matches the `paigasus-gateway` template, the PRN shape in §4.2 is verified correct against the kernel, and the out-of-scope discipline is disciplined. But several concrete items will either red CI on first implementation, or leave the two headline ACs (Postgres round-trip, gRPC health) effectively unverified. ## Findings

### BLOCKER
None. Nothing makes the skeleton infeasible; every issue below has a concrete, non-redesign fix.

### MAJOR

- **gRPC health check has zero test coverage, yet AC #1 requires it** — §12 maps AC #1 ("HTTP + gRPC health checks pass") to "`tests/health.rs` (HTTP) + `grpc.health.v1 SERVING` (gRPC)", but the §8 test matrix has only four tests and **none** starts the tonic server or calls `grpc.health.v1.Health/Check`. "Status set SERVING at startup" (§6) is code, not a test. | Why it matters: the AC is literally "gRPC health checks pass" and nothing verifies it; a regression that never registers the health service or binds `:9090` ships green. | Suggested fix: add a `tests/grpc_health.rs` that boots the tonic server on an ephemeral port and asserts `Check` returns `SERVING` (no DB needed), and list it in §8.

- **Docker-gated round-trip can silently skip forever with no CI assertion that the real path ran** — §3.1/§8 rely on a `docker_available()` guard that "returns Ok (skip)" when Docker is unreachable, and claim this is "not silent-green-forever, because CI always exercises the real path." That is an *assumption*, not a *guarantee*. If the guard misfires in CI (socket path, `DOCKER_HOST` unset, permission, a refactor bug), the ONLY test proving AC #2 skips and stays green permanently. Worse, with `taskOptions.outputStyle: buffer-only-failure` (`.moon/tasks.yml:26`) plus nextest's stdout capture, the skip `eprintln!` is **not shown** on a pass — so it is silent in CI. | Why it matters: AC #2 ("row round-trips through Postgres") is the core purpose of this skeleton and could be un-verified with no signal. | Suggested fix: gate the skip on `CI` being unset — GitHub sets `CI=true`, so in CI a Docker-absence must **fail**, not skip (`if env CI is set and Docker is absent → panic`). Convert silent-green into a hard gate.

- **Round-trip `assert eq` will fail on timestamp truncation, and timestamp provenance contradicts "pure core, no clock"** — §5 stores `created_at`/`updated_at` as `TIMESTAMPTZ` (Postgres = microsecond resolution) mapped to `chrono::DateTime&lt;Utc&gt;` (nanosecond resolution). §8's round-trip is "create → find → assert eq". A `SystemTime::now()`-derived timestamp with sub-microsecond digits is **truncated on store**, so read-back `!=` original and the `assert eq` fails. Separately: §3.7 says "`paigasus-iam-core` never touches a clock or entropy," but `Principal { …, created_at, updated_at }` (§4) needs those values at construction time, and `IdGenerator` only mints IDs — the spec never says where timestamps come from. If the DB defaults them, the in-memory `Principal` won't carry them and `assert eq` fails; if the use case reads `SystemTime`, `CreateUser` unit tests become non-deterministic (defeating the injected-ID purity story). | Why it matters: this breaks the headline round-trip test AND leaves a hole every future service copies. | Suggested fix: (a) truncate/round timestamps to microseconds before persisting/comparing (or compare with a µs tolerance); (b) decide timestamp provenance explicitly — inject a `Clock` port alongside `IdGenerator`, or have the adapter assign µs-precision timestamps and re-read after insert.

- **cargo-deny will almost certainly red on the rustls crypto backend's OpenSSL license — this is a known required exception, not "as needed"** — §11.1 hand-waves deny as "add license-allow/`[[bans.skip]]` entries as needed." `deny.toml` (`rs/deny.toml`) allows only Apache/MIT/BSD/ISC/Unicode/Zlib/MPL. `sea-orm … runtime-tokio-rustls` pulls rustls' crypto backend (`ring` or `aws-lc-rs`), whose license includes the **OpenSSL** license, which is **not** on the allow-list. The deny.toml comment on line 26 literally anticipates this ("e.g. ring's OpenSSL bit land here as deps arrive"). | Why it matters: this is the single most likely CI-red, and the mitigation is under-specified. Note the good news: `multiple-versions = "warn"` (line 29) means duplicate versions won't fail, de-risking half of §11.1. | Suggested fix: pre-commit to a concrete `[[licenses.exceptions]]` entry for the chosen crypto backend (`{ name = "ring"/"aws-lc-sys", allow = ["OpenSSL"] }`), and pin which backend sea-orm resolves so the exception is exact.

- **cargo-machete: `paigasus-iam` depends on `paigasus-proto` but M0 consumes no generated `iam` type** — §9 lists `paigasus-proto-rs` in `paigasus-iam-rs`'s `dependsOn`, and §2.4 exists only to "exercise the iam codegen path." But health is `grpc.health.v1` from `tonic-health` (its own proto), and the iam.proto has only placeholder messages with no consumer. If `paigasus-iam`'s `Cargo.toml` declares `paigasus-proto` as a dependency and no source references `paigasus_proto::`, the `machete` task (`moon.yml:26`, greps `rs/**/*.rs`) flags it → CI red. | Why it matters: the dep wiring as specified likely fails the unused-dep gate. | Suggested fix: decide explicitly — either (a) reference one generated `iam/v1` message somewhere real (e.g. a trivial construct in a test) to justify the dep, (b) add `paigasus-proto` to `[package.metadata.cargo-machete] ignored`, or (c) drop the Cargo dep and keep only the Moon `dependsOn` edge for ordering (and say so).

- **Serviceless `iam.proto` emits no `.tonic.rs` — the §9 `include!` must be prost-only, or `build` breaks** — the codebase special-cases exactly this: `paigasus-proto/src/lib.rs:18-26` includes ONLY the prost file for `common/v1` "because audit.proto declares no service, so neoeinstein-tonic emits no `.tonic.rs`". §9 says "add the `paigasus::iam::v1` module wiring (`include!`)" without noting this. An implementer copying the `gateway/v1` block (lib.rs:11-16, which includes both `.rs` and `.tonic.rs`) will `include!` a nonexistent `paigasus.iam.v1.tonic.rs` → compile error → `build` red. | Why it matters: a definite build break, easily hit by pattern-matching the wrong existing block. | Suggested fix: state explicitly that iam/v1 wiring mirrors `common/v1` (prost `.rs` only, no `.tonic.rs`).

- **"One shared `tower::ServiceBuilder`" is internally inconsistent and not type-feasible as written** — §4/§6 claim both servers are "built from a single `tower::ServiceBuilder` factory" via `fn service_layers() -&gt; ServiceBuilder&lt;…&gt;`, but the §4.2 parenthetical admits the gRPC trace layer uses `TraceLayer::new_for_grpc()` while HTTP uses `new_for_http()`. Those are **different layer types**, so one function returning one concrete `ServiceBuilder&lt;L&gt;` cannot serve both. Additionally, §10 adds `tower-http`'s `timeout` feature: `tower_http::timeout::TimeoutLayer` returns an **HTTP 408** on timeout, which is wrong for gRPC (clients expect a `grpc-status` trailer / `DEADLINE_EXCEEDED`, and tonic has its own request-timeout support). | Why it matters: this is a *pattern-setting* spec; the "shared stack" claim is misleading and an implementer will discover the types don't unify and fork anyway, then every future service inherits the confusion. | Suggested fix: drop the "one shared ServiceBuilder" framing; share only protocol-agnostic *config* (the timeout `Duration`) and build each server's stack separately with its correct trace/timeout layer.

- **`async fn` in the repository port + the axum/tonic `Send` bound is a real, unmade decision — and `async-trait` is missing from §10** — §4.1/§11.5 defer generic-vs-`dyn` to the plan and only flag `dyn` object-safety. The harder issue: native `async fn` in a trait returns a future that is **not** `Send` by default, but a repo awaited inside an axum/tonic handler on a multi-thread runtime requires `Send`. Native RPITIT doesn't express that bound without `trait_variant`/`impl Future + Send` gymnastics, which is why repository ports in axum services typically use `#[async_trait]` (boxes to `Pin&lt;Box&lt;dyn Future + Send&gt;&gt;`). §10 (deps to add) does **not** list `async-trait`, so if the plan lands on `dyn`/`async-trait`, a dep is unaccounted for. | Why it matters: this is the load-bearing template decision the whole adapter surface copies; leaving it to the plan risks a late rewrite. | Suggested fix: decide in the spec (recommend `#[async_trait]` for `PrincipalRepository` for `Send`+`dyn` ergonomics), add `async-trait` to §10, or commit to generics-only and prove the handler `Send` story.

### MINOR

- **`RepositoryError::Backend(String)` discards the underlying `DbErr`** — §4.1 stringifies the DB error, losing structured info (SQLSTATE, unique-violation detection needed for the `Conflict` variant) and the error chain for logging. Keeping the core pure (no `sea-orm` import) is right, but map `DbErr → RepositoryError` in the adapter with `Backend(Box&lt;dyn Error + Send + Sync&gt;)` (source-preserving) rather than `String`. Every future service copies this shape.

- **SeaORM `DeriveActiveEnum` cannot go on the pure-core enums** — §5 says `kind`/`status` are "SeaORM `DeriveActiveEnum`", but `PrincipalKind`/`PrincipalStatus` live in `paigasus-iam-core` which must not depend on sea-orm (§2.2). The entity must use a *separate* persistence enum (or `String`) mapped to/from the core enum in `pg_repository`. The spec should state this to avoid an implementer deriving SeaORM on the core type (a hexagonal-purity leak).

- **`Email` "light validation" is unspecified** — §4/§8 assert "Email validation" as a domain invariant but never define the rule (contains `@`? non-empty? RFC 5322-lite?). Two engineers write two validators and two tests. Pin the exact rule (recommend: non-empty, single `@`, non-empty local/domain — nothing more for M0).

- **New handwritten files need SPDX headers; new proto must pass `buf format` + STANDARD lint** — CLAUDE.md requires `// SPDX-License-Identifier: Apache-2.0` on every source file, and the CI `:fmt`/`:lint` tasks include `contracts:fmt` (`buf format --exit-code`) and `contracts:lint` (buf STANDARD). The spec never mentions either; `iam.proto` and all new `.rs` files must comply or `:fmt`/`:lint` red. (SPDX is a local convention, not separately CI-gated, but still required.)

- **`PrincipalId(Prn + Uuid)` stores a redundant UUID** — the `Prn` already exposes `resource_id()` (`prn.rs:184-187`). Storing both is defensible (UUID = PK/FK, PRN = canonical name) but note the UUID is derivable; consider `PrincipalId(Prn)` with a `.uuid()` accessor to avoid divergence.

- **`Prn::build` is fallible but `IdGenerator::new_principal_id` is infallible** — `Prn::build` returns `Result&lt;_, PrnError&gt;` (`prn.rs:155`), yet §4.1's port returns a bare `PrincipalId`. For the fixed inputs (`"iam"`, `"principal"`, valid UUID) it cannot fail, so the adapter must `.expect()`. Fine, but the spec should note the adapter unwraps a statically-infallible build.

- **Graceful-shutdown signal fan-out to two servers is unspecified** — §7 "spawn axum; spawn tonic; await both; graceful shutdown on SIGINT/SIGTERM" doesn't say how one signal reaches both servers (a single signal future can't be awaited twice) or whether "await both" is `join!` (wait for both) vs `select!` (first-exit tears down). This is exactly where two engineers diverge; pin the mechanism (e.g. `tokio::sync::watch` broadcast to both `with_graceful_shutdown`).

### QUESTIONS

- Is committing a dead placeholder `iam.proto` message to all three generated languages worth it, versus deferring `iam.proto` to M1 when a real RPC exists? The stated justification ("exercise the iam codegen path") is legitimate pattern-setting, but the message is consumed by nobody in M0 and adds drift-gate surface. Confirm the intent.
- Neither `/readyz` (needs DB) nor `IamConfig` loading (figment layering, missing-`database_url` error) has a test in §8. Are they intentionally unverified in M0, or should a config unit test + a readyz-503-when-DB-down test be added? Note `/readyz` shares the same Docker-gate exposure as the round-trip.
- Is a `.env.example` / `iam.toml.example` in scope? §7 makes `database_url` required with no default, but there's no documented way for a developer to supply it when running `main` locally.
- Was a GitHub Postgres `services:` container (with the test skipping when `DATABASE_URL` is unset) weighed against testcontainers-in-Moon-task? It avoids the daemon-detection guard entirely at the cost of one `ci.yml` block. The spec rejects it to protect the single tuned job — reasonable, but confirm the guard complexity is the accepted trade.

## What's good

- **The PRN shape in §4.2 is verified correct.** `Prn::build("iam", "", None, "principal", uuid)` (`prn.rs:155-159`) with an empty region (parse skips region validation when empty, `prn.rs:131`) and `None` org produces exactly `prn:pgs:iam:::principal/&lt;uuid&gt;`. `is_valid_label` accepts `"iam"`/`"principal"`. Accurate against the real kernel.
- **Correct posture choices that pre-empt CI pain:** `runtime-tokio-rustls` (avoids the openssl-sys C-link and matches the reqwest rustls posture), keeping `rand` native-only so `wasm-getrandom-free` (`moon.yml:107-129`) is untouched, and text-backed enums to avoid `ALTER TYPE` migrations. The reasoning in §10 about `rand`/`getrandom` not entering the wasm tree is exactly right.
- **Injected-ID purity and the `IdGenerator` port** are a clean, testable pattern worth keeping (once the parallel timestamp/clock gap above is closed).
- **Explicit, disciplined out-of-scope list (§2)** with the one-variant-enum forward-compat rationale — genuinely prevents scope creep and pre-answers "why does `PrincipalKind` have one variant."
