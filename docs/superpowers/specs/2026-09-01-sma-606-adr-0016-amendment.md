## Amendment — 2026-09-01 (SMA-606)

SMA-606 adds the tenancy audit-log and domain-event trail — an `AuditEntry` and a `DomainEvent` on
every organization, team, project and membership mutation. Two things in this ADR change.

### 1. Decision 5 — the subject space grows from 8 to 22

Decision 5 fixes the subject as the `EventType` wire string verbatim and enumerates it as
"`iam.principal.created`, `iam.role.revoked`, and the six others". SMA-606 adds fourteen:
`iam.{organization,team,project}.{created,renamed,archived,restored}` and
`iam.membership.{attached,detached}`.

**The rule is unchanged** — the subject is still the wire string verbatim, still under `iam.>` — so
stream `IAM_EVENTS`'s filter and `iam-publisher`'s `iam.>` publish grant need no edit. Only the
enumeration is now out of date, and this amendment is the correction. `ops/nats/permissions.md` §3's
reasoning about why a subject filter cannot live in a permission is likewise unaffected; it now
simply covers a wider space.

**One existing consumer is affected, and it is worth naming.** `iam.role.granted` acquires a third
emitter. `RoleService::grant` and `BootstrapAdminSeeder::seed_grant` already emit it; organization
create now does too, for the `org_admin` owner grant it writes in the same transaction. Because
`iam.role.granted` is one of the six `CONSUMER_FILTER_SUBJECTS` the `gateway-cache-invalidator`
durable filters on, **every organization create now delivers a message to that durable**. That is
wanted — a new `org_admin` grant genuinely changes authorization decisions, which is why the
subject is filtered in the first place — but it is throughput SMA-492 did not size for. The event
carries `"source": "organization_create"` in its payload so a future consumer can distinguish it
from a user-requested grant, following the convention `BootstrapAdminSeeder` established with
`"source": "bootstrap_admins"`.

### 2. The "PII-free" consequence needs a narrower statement

The consequence beginning "**`iam.>` carries the full authorization change graph**" audits the
payloads as "secret-free and PII-free (audited: principal ids and kinds, api-key ids and *display*
prefixes, grant ids and role keys — no email, no hash, no token material)". That audit was
exhaustive over the eight event types that existed when it was written.

The tenancy payloads add two fields that are not identifiers: `slug` and `name`. `slug` is
constrained by `Slug::parse`. **`name` is operator-controlled free text, and nothing constrains its
content.**

So the accurate statement is no longer "the payloads are PII-free" but:

> The payloads carry no PII **by construction** except a tenancy node's `name`, which is whatever
> an operator typed.

This changes no decision in this ADR. It changes what a reader may assume. An operator who puts a
person's name in an organization name has put it on `iam.>` and into `audit_log.detail`. The
exposure is bounded by the permissions SMA-493 provisioned — only `iam-provisioner` may subscribe
to `iam.>`, and the audit read path is Root-only — but it is now bounded **by permission rather
than by construction**, and that distinction belongs in the document that made the original claim.

The secret-free half of the audit is unaffected: no tenancy payload carries a hash, a token, or any
credential material.
