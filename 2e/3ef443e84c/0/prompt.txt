`Err(_) =&gt; Err(ApiError(TenancyError::InvalidUuid(F::NAME)).into_response())` swallows every `PathRejection` variant. Verified against `axum-0.8.9`: `MissingPathParams` and `WrongNumberOfParameters`/`UnsupportedType` are `INTERNAL_SERVER_ERROR` (`src/extract/rejection.rs:43,51`; `src/extract/path/mod.rs:445-447`); only `FailedToDeserializePathParams` is `BAD_REQUEST`. So a route whose path pattern stops matching its handler's arity — e.g. someone adds a segment to `/{sa}/api-keys/{id}` — now answers `400 invalid-uuid` on all 26 segments instead of surfacing as a 500. That is a server bug reported to the client as their mistake, which is the same category of error this ticket exists to remove.

The module doc at `path.rs:10` claims it "mirrors `authn::EnvelopeJson`, which already does exactly this". It does not: `envelope_rejection` (`http/authn.rs:112-125`) preserves `rejection.status()` and branches on the rejection kind (`TooLarge` vs `Invalid`). The new extractor discards both. Fix is to match `PathRejection::FailedToDeserializePathParams` explicitly and fall through to `rejection.into_response()` otherwise — and to soften that doc claim.

**5. `http/api_keys.rs:114` reports the wrong field name for the `{sa}` segment.** — blocks merge: no

`revoke` takes `UuidPathPair&lt;ApiKeyIdField&gt;` on `/{sa}/api-keys/{id}`, so a malformed **service-account** uuid answers `"api_key_id must be a uuid"`. That is a guess presented as fact, on the one branch whose whole thesis is that a misleading reason is a bug.

Worse, the justification is wrong. `path.rs:79-80` says "axum's `PathRejection` does not say WHICH segment failed". It does: `ErrorKind::ParseErrorAtKey { key, value, expected_type }` (`axum-0.8.9/src/extract/path/mod.rs:297`), reachable via `FailedToDeserializePathParams::into_kind()`. The extractor can name the failing segment exactly. Either read the key and map it to the right marker, or give `UuidPathPair` two markers — but do not keep a false claim about a third-party API as the reason for shipping a wrong message.

**6. No test drives a malformed uuid path segment through a real IAM router.** — blocks merge: no

Both tests that exercise the extractor (`path.rs:110-127` and `convert.rs:1112-1136`) build a synthetic `Router::new().route("/x/{id}", …)`. Nothing under `tests/` hits a real route — I grepped; the only `not-a-uuid` cases are the audit *cursor* ones. So the branch's largest behavioural change — 26 segments switching from axum's plain-text rejection to the JSON envelope, on every organization/team/project/service-account/api-key/membership/role-grant/dead-letter route — has no end-to-end coverage, and a wrong handler→marker mapping is invisible to the entire suite. Finding 5 is exactly that bug, and it survived 1003 passing tests plus a per-task review. The ledger anticipated the risk ("a wrong marker compiles and passes every test") and answered it with manual reading; one Docker-backed case (`GET /v1/organizations/not-a-uuid` → 400, `invalid-uuid`, `"organization_id must be a uuid"`) would answer it durably.

## Strengths

Do not second-guess these; they are the parts that were done well and would be expensive to redo.

- **The `&amp;'static str` payload choice (D2) is the right call and is genuinely structural.** It converts "never reflect caller input into an error body" from a discipline every future call site must remember into something the type system refuses to express. I checked all 26 construction sites; the invariant holds without exception.
- **The cursor/uuid split holds up once you see all the sites together.** Recoverability genuinely differs — a rejected cursor means "restart pagination", a rejected id means "the user typed something wrong" — and the append-only registry makes splitting-now free and splitting-later breaking. The naming deviations are both correct and correctly argued: `mutually-exclusive-fields` over `conflicting-fields` (every other `*conflict*` reason is a 409, this is a 400) and `invalid-audit-outcome` over `invalid-outcome` (`outcome` is already an overloaded token here).
- **The parity guard is real, not decorative.** It drives `to_filter` rather than raw helpers, so it also proves wiring; it pins expected reasons as `ErrorReason` values via `as_wire_reason()` rather than kebab literals, which routes every assertion through the registry *and* keeps `repo:error-code-single-site` fully covering both production adapters; and when mutation testing showed two assertions were half-vacuous, one was fixed properly (a real extractor round trip) rather than documented away.
- **The F7/F8/F9 rulings are the best process work on this branch.** F7 caught a bare literal that would have quietly blinded a gate on a production file; F8 applied the lesson forward before dispatch instead of paying another fix loop; F9 correctly refused "impractical to fix" when the machinery already existed one task earlier. Those are exactly the calls that per-task review usually misses.
- **AC-2's evidence is verifiable and I verified it independently.** All 21 surviving `InvalidPrn` sites are genuine; `http_authz.rs:222` is correctly left alone and correctly called out in advance so nobody "fixes" it.
