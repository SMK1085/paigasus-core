<result>I've read the spec (§3 of the SMA-387 design doc), the three target files, all seven vendored plugins, both CI workflows, and the Moon/proto toolchain config. Here's my adversarial review.

## Verdict: NEEDS REWORK

The core design is genuinely sharp — keeping the global `[install.arch]` remap and layering a Linux-only identity override is the correct stale-client-safe shape, and the reasoning in §3 is better than most config changes get. But this "config-only" change is subtle, and three things must be nailed down before code: the flip's success depends on an upstream resolution semantic that x86_64 CI can never validate, the proto floor's enforcement strength is load-bearing and unverified, and the lefthook half of the change is underspecified in a way that can break macOS/Windows-arm64. As written, the change can plausibly (a) silently no-op on Linux-arm64, or (b) regress stale-proto Linux-arm64 contributors to a silent 404 — the exact failure modes I was told to prioritize.

## Findings

### BLOCKER

- **The flip's correctness rests on an unverified upstream semantic, and the only test that can catch a failure is a skippable manual one** — The entire flip depends on `[platform.linux.arch] aarch64 = "aarch64"` *shadowing* the global `[install.arch] aarch64 = "arm64"` for Linux (design §3, lines 114-120). §1 (lines 69-73) explicitly flagged this as risky and demanded an upstream identity-override test — but that was written 2026-06-10, before #151 merged (06-11) and before `schema_tool-v0.18.0` shipped (06-26). The spec presents the flipped TOML as a settled fact and never restates the verification as a *merge gate*. If the shipped engine resolves identity entries as no-ops (skipping a platform-map value equal to the raw value), the flip compiles cleanly, x86_64 CI stays green (the `[platform.linux.arch]` table has only an `aarch64` key, inert on x86_64), and Linux-arm64 still resolves the nonexistent `buf-Linux-arm64` — a total silent failure of the change's only purpose. | Why it matters: x86_64 CI (`ci.yml` runs solely on `ubuntu-latest`, line 21) structurally cannot exercise the remap; AC #4's `docker run --platform linux/arm64` is the sole net, and it's a one-off manual step easy to skip. | Suggested fix: Make AC #4 a hard, non-skippable merge gate; before merge, confirm the *merged* #151 actually contains the identity-override test §1 demanded, and confirm proto 0.58.1's *bundled* schema_tool is ≥0.18.0 (not merely that the release notes mention the tables). Paste the observed `buf-Linux-aarch64` download line into the PR as evidence.

- **The proto floor is load-bearing for not regressing contributors, but its operator is contradictory and its enforcement strength is unverified** — Three coupled problems with `proto = …` in `.prototools`: (1) **Operator contradiction.** Design §3 line 127 says `proto = "&gt;=x.y.z"` (a floor); the Linear AC says `proto = "x.y.z"` (exact); every existing entry in `.prototools` (lines 1-8) is an exact pin. These are not interchangeable — an exact pin can *downgrade* CI from latest proto and changes proto's self-switch behavior. Unresolved between two authoritative sources. (2) **Enforcement unverified.** The spec claims "CI (`moonrepo/setup-toolchain` installs from `.prototools`) … enforce the floor" (lines 129-130), but `setup-toolchain` installs proto at its own `proto-version` input (default *latest*), not from `.prototools`. The `.prototools` proto pin is only honored if proto's self-version-detection auto-switches — and the spec never establishes whether that hard-fails, auto-installs+re-execs, or merely *warns*. (3) **Regression if it only warns.** At flip-over the `archs = ["x86_64"]` loud-fail guard is dropped (buf.toml line 21; design line 124). A contributor on proto &lt;0.58.1 then has: stale engine drops `[platform.linux.arch]` → global remap `aarch64→arm64` → downloads nonexistent `buf-Linux-arm64` → **silent 404, with the loud-fail now removed**. That is *worse* than the interim. The doc's claim "stale proto — Linux-aarch64 reverts to today's behavior" (lines 122-123) is wrong: "today's behavior" is the loud-fail; the actual fallback is the pre-SMA-387 silent 404. | Why it matters: Whether the floor warns vs. hard-fails is the difference between "forced upgrade" and "silent breakage on a real (if small) population." | Suggested fix: Decide the operator (recommend exact `0.58.1` to match repo convention and force determinism) and *verify empirically* what proto does locally on 0.57.x with that pin (hard-fail vs warn). If it only warns, either keep a residual arch guard or document that stale-proto Linux-arm64 silently breaks. Correct the "reverts to today's behavior" sentence.

### MAJOR

- **lefthook rewrite is underspecified and carries a macOS/Windows footgun** — AC #3 says only "apply the same platform-scoped pattern" with no exact TOML. lefthook's macOS table uses `MacOS` (lefthook.toml line 23) and its macOS/Windows arm64 assets are named `arm64` (the global remap on line 31 is what makes them resolve). The *correct* flip is identity override on Linux **only**, keeping the global — but "same pattern" could be misread as "add platform-scoped overrides generally," and an implementer who adds `[platform.macos.arch] aarch64 = "aarch64"` would break macOS-arm64 on new engines (resolving nonexistent `lefthook_{ver}_MacOS_aarch64`). The buf AC #1 has explicit guardrails ("Do NOT move to macos/windows"); AC #3 has none. Separately: lefthook publishes duplicate `Linux_aarch64`/`Linux_arm64` (identical sha256), so lefthook Linux-arm64 *works today* and even survives the stale-engine path — the flip is pure churn with marginal defensive value, and the spec doesn't weigh bundling it now (added footgun risk) vs. deferring until upstream actually drops the alias (the comment already records that trigger). | Why it matters: ambiguity here can break the *primary* dev platform; the churn buys ~nothing now. | Suggested fix: Either give the exact lefthook TOML (linux-only identity override, global kept, macos/windows untouched) and confirm lefthook's Windows-arm64 asset name, or defer lefthook to a comment-only change and drop it from this PR's scope.

- **No permanent automated coverage on the only platform the change affects** — `ci.yml` runs solely on `ubuntu-latest` (x86_64), which never exercises the arch remap. The fix would be verified once via manual docker (AC #4) and then *never again*, despite the design itself acknowledging buf pin bumps are manual and asset renames are "detected at next install on the affected platform, not by CI" (§2, lines 96-98). Meanwhile `prebuild.yml` already provisions `ubuntu-24.04-arm` runners (lines 31, 33) — a permanent Linux-arm64 smoke step (`proto install buf` + assert `buf-Linux-aarch64`) is essentially free and would catch a future proto release silently changing platform-scoped resolution, or a buf asset rename. | Why it matters: a brittle upstream-resolution-order dependency with zero regression protection on its target platform. | Suggested fix: Add a small `ubuntu-24.04-arm` CI step that runs `proto install buf` and greps the resolved asset; gate it in the same workflow.

- **macOS-arm64 regression on the new engine is absent from the flip test plan** — The new schema engine changes the `{arch}` resolution code path. On macOS there is no `[platform.macos.arch]` table, so resolution must fall through: platform map (absent) → global `install.arch` (arm64) → `buf-Darwin-arm64`. This *should* work, but it's a different code path than the engine the repo runs today, and it governs the primary dev platform. The §3 / Testing section never lists "re-verify macOS-arm64 `proto install buf` against the new proto + flipped TOML." The dev is on Apple Silicon, so this is a one-command check. | Why it matters: if the new engine's global fallthrough differs, every macOS contributor's buf/lefthook install breaks after they upgrade proto — and CI (Linux) wouldn't catch it. | Suggested fix: Add to the flip checklist: with proto ≥0.58.1 and the flipped TOML, confirm `proto install buf` and `proto install lefthook` still resolve `*-Darwin-arm64` locally.

### MINOR

- **TOML subtable placement gotcha** — `[platform.linux]` (buf.toml lines 20-23) already holds bare keys (`download-file`, `checksum-file`). In TOML, once `[platform.linux.arch]` is opened you cannot add more bare keys to `[platform.linux]`. The design snippet (lines 114-120) shows the new table next to `[install.arch]`, not integrated into the existing `[platform.linux]` block, inviting an implementer to insert `[platform.linux.arch]` *before* `download-file` — which would silently make `download-file` a key of the arch subtable. (Caught by CI on x86_64, but worth pre-empting.) | Suggested fix: Specify exact placement (the `[platform.linux.arch]` header after all bare keys of `[platform.linux]`, or as the last table before `[install]`).

- **Comment/doc debt left stale** — Post-flip, buf.toml's interim comment (lines 8-15, "Linux is restricted to x86_64… Flip-over is SMA-411") and lefthook.toml's comment (lines 10-13, "If upstream drops that alias, apply the platform-scoped pattern") are both false, and the SMA-387 design doc's `Status: Approved` / §3 "after upstream ships" framing is now past-tense. The spec mentions rewriting buf.toml's comment only implicitly. | Suggested fix: Make rewriting both TOML headers and updating the design doc's status an explicit task in the flip PR.

- **No dedicated SMA-411 spec/plan despite the repo convention** — CLAUDE.md mandates brainstorm→spec→plan→implement, date-prefixed per Linear issue; I found no `*sma-411*` doc under `docs/superpowers/`. SMA-411 is being implemented from §3 of another issue's doc plus the Linear AC. Defensible for a tiny change, but it means the verification gates above live only in scattered prose. | Suggested fix: Either write a short SMA-411 spec capturing the merge gates, or explicitly note in the PR that §3 + the AC are the authoritative spec.

- **Docker verification mechanics underspecified** — AC #4 doesn't say how the container obtains proto ≥0.58.1 (the dev's local proto is 0.57.2 and is irrelevant inside the container), nor that the repo must be mounted and run from its root so the relative `buf = "file://./.proto/plugins/buf.toml"` (.prototools line 21) resolves. | Suggested fix: Spell out the container recipe (install proto ≥0.58.1, mount repo, run from root) so the verifier exercises the new engine and the vendored plugin.

## What's good

- **The stale-client safety analysis is the spec's strongest asset** (§3, lines 105-125): keeping the global `[install.arch]` and adding a *Linux-only* identity override, rather than relocating the remap to macOS/Windows, is exactly right and correctly protects the primary dev platform on old engines. Preserve this reasoning verbatim.
- **Coupling the proto floor to the flip is the correct sequencing** — the flipped TOML is inert (and on stale engines, harmful) without the new schema engine, so they must land together. Resist any suggestion to split them.
- **CI already runs latest proto** (`setup-toolchain` with `cache: false`, ci.yml lines 45-50, no `proto-version` override → latest, which today is ≥0.58.1). This meaningfully de-risks the bump *for CI specifically*: the floor largely codifies CI's status quo, so the other six vendored plugins are already proven on 0.58.x. The residual risk is concentrated on local contributors, which is where the review attention belongs.
