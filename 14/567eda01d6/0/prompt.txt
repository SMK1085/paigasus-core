#### Important (Should Fix)
- **`create_user` is not atomic — a failed second insert leaves an orphaned `principal` row.** `pg_repository.rs` (`create_user`, ~lines 22-33) does `principal.insert(&amp;self.db).await?` followed by a separate `user.insert(&amp;self.db).await?` with no `self.db.begin()`/`db.transaction(...)` wrapper. If the `user` insert fails (e.g. duplicate email, unrelated DB hiccup), the `principal` row is already committed with no corresponding `user` row. Consequences: (1) a permanently orphaned `principal` row with no cleanup path; (2) a caller retry with the *same* `Principal`/`User` pair will now get a spurious `Conflict` on the `principal` insert (duplicate `id`/`prn`) even though the logical create never succeeded — the retry can't distinguish "already created" from "partially created." `find_user` itself still behaves correctly in this state (returns `Ok(None)` because the `user` row is missing), so it doesn't lie to callers, but the leaked row and the broken-retry semantics are a genuine data-layer correctness gap in what's flagged as the most correctness-sensitive task so far. Fix: wrap both inserts in a single `DatabaseConnection::transaction` (or `db.begin()`/`commit()`). This is not mentioned anywhere in the implementer's report as a known/accepted limitation, which is itself a gap — a reviewer or future maintainer has no signal this exists.
