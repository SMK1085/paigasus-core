## 4. `next.config.ts` (verbatim) and `createNextConfig`

```ts
import { fileURLToPath } from 'node:url';
import { createNextConfig } from '@paigasus/next-config';

export default createNextConfig({
  zone: 'iam',
  basePath: '/iam',
  outputFileTracingRoot: fileURLToPath(new URL('../..', import.meta.url)),
  extend: { experimental: { authInterrupts: true } },
});
```

`createNextConfig` (`ts/packages/paigasus-next-config/src/index.ts`) accepts `{ zone, basePath, assetPrefix?, outputFileTracingRoot, extend? }`. It:
- rejects `extend.env` (env is factory-owned; deployment values must go through `@paigasus/next-config/runtime` instead)
- rejects a `zone` with leading/trailing whitespace or empty
- canonicalizes `basePath` via `canonicalBasePath`
- merges `SOURCE_ONLY_PACKAGES` (`@paigasus/app-shell`, `@paigasus/auth`, `@paigasus/discovery`, `@paigasus/kernel`, `@paigasus/next-config`, `@paigasus/proto`, `@paigasus/sdk`, `@paigasus/ui`) into `transpilePackages`
- unconditionally forces `output: 'standalone'` (cannot be overridden by `extend`)
- writes `env: { PAIGASUS_COMPILED_ZONE, PAIGASUS_COMPILED_BASE_PATH }` (build-time-baked image identity — the only two "NEXT env" values allowed, distinct from `NEXT_PUBLIC_`)

A second app would call this the same way with a different `zone`/`basePath` (e.g. `zone: 'gateway', basePath: '/gateway'` per the `.env.local.example` comment referencing SMA-512).

## 5. Auth wiring

- **Route handler**: `app/auth/[...auth]/route.ts` — one catch-all handler mounting `createAuthRouteHandler` from `@paigasus/auth/server`, keyed by a `WeakMap&lt;AuthRuntime, handler&gt;` so the handler is built once per runtime; `GET`/`POST` both delegate to `handle()`.
- **`proxy.ts`** (repo root of the app) — Next 16's name for middleware. Imports only `@paigasus/auth/middleware` (never `/server` or the sdk — enforced by `paigasus-next-config` boundary tests). Two jobs: (1) cookie-presence-only auth gate via `createAuthMiddleware({ publicPaths: [...authRoutePaths(), '/', '/healthz'], loginPath: '/auth/login' })`; (2) mints a per-request correlation id header and a request-path header. `config.matcher` excludes `_next/static`, `_next/image`, `favicon.ico`.
- **`lib/auth.ts`** — the composition root: `authRuntime()` calls `getAuthRuntime(getRuntimeConfig(), { logger, resolver: createIntrospectPrincipalResolver(...) })`; also defines `SESSION_COOKIE_NAME = '__Host-pgs_sid'` (not exported by `@paigasus/auth` itself).
- **`lib/iam.ts`** — per-request React `cache()`-wrapped accessors: `currentSession` (redirects to login), `iamClients`, `optionalSession`, `iamClientsForAction` (server-action-safe, returns a `relogin` failure instead of redirecting), `sessionToken`.
- **`lib/correlation.ts` / `lib/correlation-header.ts`** — reads/writes `CORRELATION_HEADER` and `REQUEST_PATH_HEADER` via `next/headers`; `FORBIDDEN_VIEW_CORRELATION` constant records whether the 403 view can read the header.
- **`lib/prn-tenancy.ts`** — hand-written PRN parser for IAM's three tenancy shapes (`organization`/`team`/`project`), held to parity with the Rust kernel by `tests/unit/prn-tenancy.test.ts` replaying `rs/crates/libs/paigasus-kernel-parity/vectors/**`. Recorded ADR-0005 exception (kernel napi/wasm bindings don't work in a Next build).
- **`lib/config.ts`** — the app's one `defineRuntimeConfig` call, composing `authEnvShape` + `discoveryEnvShape` + `PAIGASUS_IAM_GRPC_URL` (a zod transform validating an absolute http(s) URL with no credentials/query/fragment) and a refined `PAIGASUS_SERVICES` requiring an `iam` entry.
- Other `lib/` files: `authorize.ts` (`mayI`), `discovery.ts`, `errors.ts`, `form.ts`, `iam-clients.ts`, `logger.ts`, `nav.ts`, `paging.ts`, `principal*.ts`, `scopes.ts`, `tenancy-path.ts`.

## 11. `repo:next-public-free` and `repo:next-env-drift` gates

- **`repo:next-public-free`** (root `moon.yml:903-943`, script `ci/next-public/run.sh`): bans `NEXT_PUBLIC_` anywhere under `ts/` (packages included, not just apps — a source-only package inlines the same way when transpiled) and requires every app's Next config to go through the `@paigasus/next-config` factory. Discovery is **generic**: `APP_CONFIG_GLOB='ts/apps/*/next.config.[tjmc][sj]*'` (`ci/next-public/run.sh:184`), so a second app is automatically covered, no registry edit needed. Runs `--self-test` and `--negative-control` before the real run (all three required by `set -euo pipefail`, pinned by `SELF_SCHEDULED_GATES`). `inputs` use `ts/**/*` minus negated `.next`/fixture-`.next` globs (also generic `ts/apps/*/...`).
- **`repo:next-env-drift`** (root `moon.yml:130-155`, script `ci/next-env/run.sh`): asserts the committed `next-env.d.ts` matches what `next typegen` emits. **Hard-coded to one app**: `APP='ts/apps/iam-console'` (`ci/next-env/run.sh:26`); the moon task's `deps: ['iam-console-ts:build']` and `inputs` (`ts/apps/iam-console/{next-env.d.ts,next.config.ts,tsconfig.json,app/**/*}`, plus `ts/pnpm-lock.yaml`) are also iam-console-only. A second app would need either its own copy of this gate/script (parameterized by app dir) or an extension of this one to loop over both apps — currently it silently does not check a second app's `next-env.d.ts` at all.

## 12. Dockerfile / standalone image build

- **No Dockerfile exists for iam-console** (or for any Next.js app) anywhere in the repo. `find -iname "Dockerfile*"` only finds `rs/Dockerfile` (the Rust services image, used for `paigasus-iam` and `paigasus-gateway` binaries — unrelated to Next/console apps).
- `.github/workflows/images.yml` only triggers on `rs/Dockerfile` changes (line 28) and builds/smokes the two Rust service images via `ci/images/run.sh`; it has no Next/console image target.
- `ci/images/run.sh` (`build`/`smoke`/`all` subcommands) is entirely Rust-service-specific: `crate_for()` maps only `iam`→`paigasus-iam` and `gateway`→`paigasus-gateway`; `assert_pins()` checks `rs/Dockerfile`'s Rust toolchain/Ubuntu/chisel pins; `smoke()` runs `paigasus-gateway:dev` and `paigasus-iam:dev` containers with Postgres. - **Streaming (SSE):** yes. `chat.rs:121-144` proxies OpenAI's SSE stream verbatim as `Content-Type: text/event-stream`, unbuffered, and if the upstream fails mid-stream it emits one terminal `data: {"error":{...,"code":"upstream-error"}}\n\n` frame (`chat.rs:63`, `terminal_sse_error_stream` at `chat.rs:206-220`) rather than changing the already-committed HTTP status. - **Ports/transports:** **one HTTP port only, no gRPC server** (main.rs:6-7: "one HTTP port, no gRPC server, no DB"). Config key `http_addr` (default `0.0.0.0:8088`, `config.rs:187`). ## 6. `ts/packages/paigasus-auth` — multi-zone story

- `PAIGASUS_ZONE`/`PAIGASUS_ZONES` are **not** declared by `paigasus-auth`'s own `authEnvShape` — they are explicitly forbidden there because they're owned by `@paigasus/next-config`'s `defineRuntimeConfig` (`src/config.ts:6-9`, "throws if an extra shape declares `PAIGASUS_ZONE` or `PAIGASUS_ZONES`"). They arrive into `createAuthRuntime` via the composed config type `ComposedConfig = AuthEnv &amp; { PAIGASUS_ZONE: string; PAIGASUS_ZONES: Record&lt;string,string&gt; }` (`src/runtime.ts:51-54`).
- **The reject-memory-with-multiple-zones rule**, `src/runtime.ts:105-113`:
  ```ts
  if (cfg.PAIGASUS_SESSION_STORE === 'redis') {
    requireRedisUrl(cfg); // Invariant 1
  } else if (Object.keys(cfg.PAIGASUS_ZONES).length &gt; 1) {
    throw new AuthConfigError('PAIGASUS_SESSION_STORE cannot be "memory" when PAIGASUS_ZONES declares more than one zone');
  }
  ```
  Rationale in the comment directly above it: "the memory store... is single-process... under multi-zone the zones share nothing — a user who logs in on zone A is anonymous on zone B... A startup error beats that silent wrong answer."
- README (`ts/packages/paigasus-auth/README.md:84-94`) restates this: each zone in a multi-zone deployment is a **separate Next process**; under `memory` a user signed in on zone A is anonymous on zone B; `createAuthRuntime` refuses to start with `memory` + &gt;1 zone; use `redis`.
- **Cookie**: `src/http/cookies.ts:21` — `export const SESSION_COOKIE = '__Host-pgs_sid';`. Attributes from `serializeCookie` (`cookies.rs`… actually `cookies.ts:46-52`): `HttpOnly`, `Secure`, `SameSite=Lax`, **`Path=/`**, no `Domain` (forced by the `__Host-` prefix). README: "all zones share **one cookie on one origin**" (README.md:132-133) and design comment in `runtime.ts:75`: `/** All zones share one cookie on one origin (design doc § 6.7) — never per-zone, never configurable. */ cookieDomainless: true`.
- **What makes a second zone able to log a user in independently:** with `PAIGASUS_SESSION_STORE=redis`, all zones/processes on one origin share **one Redis-backed session store** (`keyPrefix: ''`, no per-zone prefix — `runtime.ts:140-148`, comment: "All zones share ONE store (design doc § 6.7) — no per-zone key prefix to configure") and **one `__Host-pgs_sid` cookie scoped `Path=/`** across the whole origin. So a gateway-console zone doesn't need its own login flow at all for an *existing* session — it reads the same cookie, looks it up in the same Redis store, and sees the user already authenticated. It *does* still need its own `/auth/login`, `/auth/callback`, `/auth/logout`, `/auth/logout/callback` routes mounted under its own base path (`README.md:105-125`, `createAuthRoutes`), each zone deriving its own OIDC redirect URIs from `PAIGASUS_PUBLIC_ORIGIN + &lt;this zone's basePath&gt; + /auth/callback` (`runtime.ts:129-130`) — so a user landing directly on the gateway zone with no session can still independently kick off its own OIDC round trip, which then writes the one shared cookie/session record any zone can subsequently read.
- Per-zone runtime singleton is cached under a **zone-keyed** `Symbol.for` slot (`runtime.ts:196-230`, `RUNTIME_KEY_PREFIX = 'paigasus.auth.runtime.v1'`, `runtimeKey(zone)`), specifically so two zone apps composed into one process (a documented future case, SMA-513) don't collide on one runtime.

### Control composition

The four controls apply three different tests for "an app":

| Control | Test | Set today | Loosest → strictest |
|---|---|---|---|
| `ts/eslint.config.js` + `next-app-rules.test.ts` | any directory under `ts/apps/` | `{iam-console}` | loosest |
| `ci/next-env/run.sh` liveness | directory with a `package.json` | `{iam-console}` | middle |
| `check_tailwind_guard_invocations` | directory with a `moon.yml` | `{iam-console}` | **strictest** |
| `ci/next-env/run.sh` check set | directory with a `next.config.[tjmc][sj]*` | `{iam-console}` | (the thing being asserted) |

The three sets agree today, so nothing is currently wrong. The divergence is dangerous in one direction only, and the branch picked that direction for the wrong control.

- **Loose is safe here.** The ESLint derivation emitting a block for a leftover directory costs an inert `files:` glob. `next-app-rules.test.ts` derives the same way, so the two cannot disagree.
- **Strict is unsafe here.** `(d / "moon.yml").is_file()` is a filter that *removes* apps from scrutiny. An app directory with no `moon.yml` is excluded and never reported. That re-creates one instance of the exact silent skip the check exists to close (triage item 2). It is narrow — an app with no `moon.yml` has no build, no test and no e2e, which is a much louder omission — but the filter buys nothing and costs the guarantee.
- **The middle test is the best-judged of the three.** Requiring a `package.json` before demanding a `next.config.*` is correct, and the stated reason (a leftover `node_modules`/`.next` directory from a rename) is a real shape. The comment even names the pnpm `apps/*` glob as the precedent. I would adopt this test for the tailwind check too.

One further divergence, this one between a gate and its own inputs: `ci/next-env/run.sh` discovers `next.config.[tjmc][sj]*` (six extensions) while `moon.yml`'s `next-env-drift` inputs pin only `ts/apps/*/next.config.ts`. `repo:next-public-free`'s self-test explicitly exercises the `.mjs` shape, so a `.mjs` app is a supported shape in this repo. ### A. `lib/auth.ts` — full quote

```ts
// SPDX-License-Identifier: Apache-2.0
//
// The auth composition root (spec § 4.2). getAuthRuntime is a PROCESS singleton that returns a
// Promise (ts/packages/paigasus-auth/src/runtime.ts:185), and its first call fixes the resolver and
// the logger for the life of the process. Nothing here runs at module scope.
import 'server-only';
import { getAuthRuntime, type AuthRuntime } from '@paigasus/auth/server';
import { getRuntimeConfig } from './config';
import { requestCorrelationId } from './correlation';
import { iamClientsForToken } from './iam-clients';
import { logger } from './logger';
import { createIntrospectPrincipalResolver } from './principal-resolver';

/**
 * The session cookie's name. @paigasus/auth does not export it from any entry an app may import,
 * so it is written here once; tests/unit/session-cookie.test.ts proves that @paigasus/auth's own
 * middleware treats exactly this name as the session.
 */
export const SESSION_COOKIE_NAME = '__Host-pgs_sid';

/**
 * The runtime is a process singleton, but `clientsForToken` runs PER REQUEST, inside the login
 * callback's route handler. So it reads the correlation id there, and the login-time IAM calls
 * (GetServiceInfo, Introspect) carry the same id as every later call of that request. proxy.ts sets
 * the header on `/auth/callback` too — the route is public, which makes the middleware allow it, not
 * skip the header. Outside a request scope `requestCorrelationId()` answers null, never throws.
 */
export function authRuntime(): Promise&lt;AuthRuntime&gt; {
  return getAuthRuntime(getRuntimeConfig(), {
    logger,
    resolver: createIntrospectPrincipalResolver({ clientsForToken: async (token) =&gt; iamClientsForToken(token, await requestCorrelationId()), logger }),
  });
}
```

What it composes: it is a pure **composition root**. It calls `getAuthRuntime()` (from `@paigasus/auth/server`, staying in the shared package) with three things assembled from local lib pieces: (1) `getRuntimeConfig()` from `lib/config.ts`, (2) `logger` from `lib/logger.ts`, (3) a `resolver` built by `createIntrospectPrincipalResolver` from `lib/principal-resolver.ts`, whose `clientsForToken` dependency is itself composed inline from `lib/iam-clients.ts`'s `iamClientsForToken` plus `lib/correlation.ts`'s `requestCorrelationId`. It also owns one bare constant, `SESSION_COOKIE_NAME`, which is app-local knowledge (not exported by `@paigasus/auth`) pinned by a test.

For the shared-package split: `authRuntime()` itself is generic wiring (config → logger → resolver → `getAuthRuntime`) and could move, provided the shared package receives `ConsoleLogger`-shaped and `IamClients`-shaped types as generic parameters/ports rather than the concrete lib types. `SESSION_COOKIE_NAME` is a leaf constant that could move with it (it's not app-specific, just undocumented upstream). What must stay app-specific is whichever module actually calls `getRuntimeConfig()` — since `getRuntimeConfig`/`getPublicConfig` are produced by this app's own `defineRuntimeConfig()` call in `lib/config.ts`, and each app in the workspace instantiates its own.

### D. `lib/config.ts` — full `defineRuntimeConfig` call with the two requested pieces

Full relevant excerpt (whole file was already quoted above under the per-file inventory; the specific parts asked for):

```ts
/** Why `value` is not an acceptable IAM gRPC address, or null when it is. */
function grpcUrlProblem(value: string): string | null {
  if (!URL.canParse(value)) return 'must be an absolute URL';
  const url = new URL(value);
  if (url.protocol !== 'http:' &amp;&amp; url.protocol !== 'https:') return 'must use http: or https:';
  if (url.username !== '' || url.password !== '') return 'must not carry credentials';
  if (url.search !== '' || url.hash !== '') return 'must not carry a query or a fragment';
  return null;
}

/**
 * IAM's gRPC address. A separate key from PAIGASUS_SERVICES.iam because IAM listens on two
 * addresses: HTTP on 8080, which discovery probes, and gRPC on 9090, which the SDK calls
 * (rs/crates/services/paigasus-iam/src/config.rs:811-812).
 *
 * One transform, not a chain of refines: a refine that calls `new URL` after a failed
 * `URL.canParse` refine would THROW, because zod 4 runs every refine. The value is canonicalized
 * to `&lt;origin&gt;&lt;path&gt;` with no trailing slash, the form @paigasus/discovery gives its addresses.
 * The message never contains the value (next-config renders only the issue code for this key).
 */
const iamGrpcUrl = z.string().transform((value, ctx) =&gt; {
  const problem = grpcUrlProblem(value);
  if (problem !== null) {
    ctx.addIssue({ code: 'custom', message: problem });
    return z.NEVER;
  }
  const url = new URL(value);
  return `${url.origin}${url.pathname.replace(/\/+$/, '')}`;
});

/** discovery's service map, plus one rule: the console cannot run without an `iam` entry. */
const servicesWithIam = discoveryEnvShape.PAIGASUS_SERVICES.refine((services) =&gt; Object.hasOwn(services, 'iam'), { error: 'must contain an "iam" entry' });

export const { getRuntimeConfig, getPublicConfig } = defineRuntimeConfig({
  ...authEnvShape,
  ...discoveryEnvShape,
  PAIGASUS_SERVICES: servicesWithIam,
  PAIGASUS_IAM_GRPC_URL: iamGrpcUrl,
});

export type ConsoleConfig = ReturnType&lt;typeof getRuntimeConfig&gt;;
```
(`lib/config.ts:16-56`)

This is the strongest signal that `lib/config.ts` must stay in the app (or become a thin per-app instantiation of a shared factory): the `defineRuntimeConfig` call is a **merge of three schema sources** (`authEnvShape`, `discoveryEnvShape`, and one app-owned key `PAIGASUS_IAM_GRPC_URL`) plus one app-specific cross-cutting refinement (`servicesWithIam` requiring an `iam` entry). A shared package could export `grpcUrlProblem`/`iamGrpcUrl`-shaped helpers, but the actual `defineRuntimeConfig({...})` invocation is inherently one-per-app.

### F. `lib/discovery.ts` — full quote, four Redis preconditions, lazy-singleton shape

## K. `boundaries.test.ts` — reverse-liveness loop and one ALLOWED/DENIED row

Reverse-liveness loop (`ts/packages/paigasus-next-config/tests/boundaries.test.ts:242-266`):
```ts
it('every rule scope has a matching entry in the preset', () =&gt; {
  // Indexed through a typed local rather than a chained member access: `noUncheckedIndexedAccess`
  // makes `entry.files?.[0]` `string | string[] | undefined` — `boundaryRules` is typed as
  // ESLint's own `Linter.Config[]`, whose `files` entries can themselves be a nested `string[]`,
  // not only a plain glob string. Narrowed with a `typeof` guard rather than a cast, so a config
  // entry that actually used the nested-array form would fail loudly here instead of being
  // silently coerced.
  const scoped = boundaryRules.map((entry) =&gt; {
    const label = entry.name ?? '(unnamed boundary entry)';
    const first: string | string[] | undefined = entry.files?.[0];
    expect(first, `${label} declares no files glob`).toBeDefined();
    expect(typeof first === 'string', `${label} files[0] is a nested string[], not a plain glob — this test does not handle that shape`).toBe(true);
    return typeof first === 'string' ? first.split('/**')[0] : '';
  });
  for (const dir of Object.keys(BOUNDARY_SCOPES)) {
    expect(scoped).toContain(dir);
  }
  // And the REVERSE. The loop above proves every declared scope has a rule; on its own it says
  // nothing about a rule added WITHOUT a scope entry, which would get no liveness coverage at
  // all — the package could land under a different directory name and the rule would sit
  // permanently inert with nothing to notice.
  for (const dir of scoped) {
    expect(Object.keys(BOUNDARY_SCOPES), `the ${dir} rule has no BOUNDARY_SCOPES entry, so nothing proves its files glob still matches a real directory`).toContain(dir);
  }
});
```

This is exactly the mechanism a new shared package's boundary block must satisfy: its `files[0]` glob, split at `/**`, must equal a key present in `BOUNDARY_SCOPES` — in both directions.

One DENIED row and one ALLOWED row (showing the row shape — `readonly [label, filePath, source]`, run through `it.each`):

The only place in the whole repo where a Playwright run touches `testcontainers`/Redis at all is `@paigasus/auth`'s E2E tier (`ts/packages/paigasus-auth/tests/e2e/global-setup.ts` + `playwright.config.ts`) — and even there, the container start happens at **`playwright.config.ts` module-evaluation / `globalSetup`**, not inside a `test.extend` worker fixture, precisely because (per that file's own header) Playwright runs every `webServer` `setup()` before any `globalSetup`, and starting containers inside a worker fixture would be too late for a `webServer` block that needs the Redis URL to construct its command.
