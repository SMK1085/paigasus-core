## Issues

No **Critical** or **Important** issues. All findings are **Minor** / cosmetic.

**Minor**

- **M-A — spec §4.1 `describe_*!` help text not implemented.** `rs/crates/libs/paigasus-observability/src/lib.rs:29` (`init`) sets buckets + installs the recorder but emits no `describe_counter!/gauge!/histogram!`, so the exposition carries no `# HELP` lines. Why it matters: operators reading raw `/metrics` lose the inline descriptions the spec called for. Mitigated by the RUNBOOK catalog. Fix: add `describe_*!` calls in `init` (or accept as follow-up).
- **M-B — dead whitelist consts + inaccurate RUNBOOK.** `names.rs:62`/`:65` define `PROM_BUILTINS` and `PROMQL_TOKENS`, but `tests/drift.rs` uses a prefix-anchored (`^(iam|gateway)_…`) extractor and references **neither** (confirmed by grep). Yet RUNBOOK §5 step 4 states the test asserts membership in `names::PROM_BUILTINS`/`names::PROMQL_TOKENS`. Why it matters: the doc describes a mechanism the test doesn't use; the consts are vestigial (public, so no dead-code warning). Fix: delete the two consts and correct RUNBOOK §5, or actually use them.
- **M-C — IAM carries an unused `metrics-exporter-prometheus` dev-dep with a false comment.** `rs/crates/services/paigasus-iam/Cargo.toml:143` claims "`tests/metrics.rs` names `PrometheusHandle` directly," but grep finds **zero** references to `metrics_exporter_prometheus`/`PrometheusHandle` anywhere in IAM — `.render()` is callable on `init()`'s inferred return without the direct dep (exactly why commit `78a6d05` pruned gateway's identical dep). The pruning commit missed IAM's. `:machete` does not flag it (I ran `cargo-machete rs/crates/services/paigasus-iam` → clean), so it is not a gate failure. Fix: drop the dev-dep + comment.
- **M-D — minor cross-service shutdown inconsistency.** IAM's separate metrics listener spawns into the shared `JoinSet` on the common watch channel (`main.rs`), while the gateway uses a detached `tokio::spawn` + a second `shutdown_signal()` (`paigasus-gateway/src/main.rs:3546`). Functionally both serve `/metrics` with graceful shutdown, but the gateway's detached task can be dropped abruptly at process exit (harmless for a scrape endpoint). Consider aligning on the IAM pattern.

## Triage of the 5 accumulated findings

1. **IAM 404-fallback uncounted vs gateway `&lt;unmatched&gt;` — FOLLOW-UP.** Confirmed real: IAM's layer lives inside `app_routes`, so the top-level 404 falls outside it; the gateway's `.layer()` wraps the whole tree incl. fallback. It's a bounded, cosmetic completeness gap (no cardinality/privacy risk), and the spec mandates no 404 counting. Not a blocker.
2. **Relay `ticks_total{result="error"}` branch untested — FOLLOW-UP.** The error arm is trivial (one counter bump + the pre-existing `warn!`), and deterministically triggering a tick error needs a fault-injecting publisher/DB. Low risk; worth a small fault-injection test later.
3. **`ticks_total` test wall-clock race (10ms poll vs 300ms, ~30×) — FOLLOW-UP.** The 300ms window also absorbs real Postgres I/O, so the margin is pragmatic rather than generous, but a single tokio timer firing within 30× is very unlikely to flake. Acceptable; could be hardened later.
4. **`TargetDown` in `gateway.rules.yml` not a shared file — FOLLOW-UP.** Functionally correct today — both rule files load via `rules/*.rules.yml`, both test files exercise it, and `up==0` is target-agnostic. Pure organization; the only latent risk is that deleting gateway rules would silently drop IAM's `TargetDown`. Move to a shared `common.rules.yml` when convenient.
5. **`audit_log` non-partitioned; RUNBOOK documents interim batched-DELETE — FOLLOW-UP (out of this cycle).** Not a defect of this branch — it's a gap in an earlier merged slice that this cycle only *documents*, and it's already tracked in spec §13 / RUNBOOK §6. The RUNBOOK is commendably honest about it. No action for this PR; keep the existing follow-up.

None of the five is more severe than Minor.
